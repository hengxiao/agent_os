# 对比报告:book-en/chapter8.md(Agent Self-Evolution)× Agent OS DESIGN.md

> 评审对象:《Agent Self-Evolution》全章(323 行,已通读)
> 对照基准:DESIGN.md v0.3(§1-§14)
> 总体判断:**关联度中等偏高**。该章不讲内核机制,讲"Agent 如何不动权重地持续变强"的方法论与工程实践;但它产出的每一类"经验产物"(Skill 文档、代码工具、工作流程序、经验条目)恰好都是我们内核各注册表的"写入方",而我们的设计目前只有"加载/分发"视角,没有"生成/演化"视角。该章为 Skill Registry、Tool Registry、Sidecars、Logic Kernel 提供了明确的需求来源和验证依据。

## 章节内容概要

本章主题:**自我进化 = 外置化学习(externalized learning)**,即在不做 post-training、不改模型参数的前提下,把经验从"具体记录"蒸馏为"通用模式",持久化到模型之外。核心论断与机制清单:

**理论起点(Why Agents Don't Learn Automatically)**
- 注意力机制本质是检索而非推理:把全部历史塞进无限长的 context,模型也只会"记住"不会"蒸馏";叠加 context rot,检索质量还会衰减。结论:**学习不会自动发生,必须显式设计(learning must be explicitly designed)**。
- 三种学习范式定位:post-training(改权重,固化策略)、ICL(会话内临时适应)、externalized learning(外置持久化,可解释、可审计、可修改)。三者协同而非竞争。

**外置化学习的三种产物(Table 8-1)与选型规则**
- Knowledge Base Entry(事实与规则,语义检索/grep)、Dedicated Code Tool(可重复的操作序列,固化为代码)、Skill Document(复杂但易变的工作策略,自然语言文档按需加载)。
- 选型口诀:纯事实进知识库;高频、参数重的流程固化为代码工具;含策略判断、易变的流程写成 Skill 文档。

**机制分层(Table 8-2)**:知识蒸馏(Strategy Summary / Workflow Recording / Failure Reflection)→ 知识组织(Skills / Sleep Consolidation)→ 知识应用(System Prompt Optimization)→ 工程支撑(Cross-Session Continuation)。

**关键机制与案例**
- **策略总结(Experiment 8-1, gaia-experience/AWorld)**:成功轨迹经 LLM 反思蒸馏为结构化经验,向量化入库;新任务先语义检索相似经验注入系统提示。入库标准是**可迁移性(transferability)**。
- **工作流录制与回放(Experiment 8-2, browser-use-rpa)**:录制动作序列(动作类型 + XPath + 参数 + 执行后验证信息),LLM 生成语义标签入库;回放期用参数化模板 + 轻量 LLM 抽参,失败则标记"可能过期"并回退学习模式重新录制。
- **PreAct(footnote,arXiv:2606.17929)**:把工作流录制严格化——成功轨迹编译为**带验证谓词(verification predicate)的状态机程序**,回放时每个动作前先对真实屏幕校验谓词("look first, then act");**入库前验证门(pre-storage verification)**:编译后重置环境从头回放,用基准 evaluator 确认任务真完成才入库,防止"步骤全跑完但任务没完成"的坏程序污染库。命中缓存的重复任务快 8.5–13 倍。原则:**程序性记忆需要验证门,否则自我改进循环会腐坏**。
- **从失败学习(Reflexion, arXiv:2303.11366)**:失败后自然语言反思存入情景记忆,下次同类任务读回;产物形态为**错误模式库**与**负规则(negative rules)**。语言化反思比标量奖励带宽高得多。
- **Skills 与 Skill Creator(Anthropic)**:Skill = 岗位手册,人可读、可审计、可移植;Skill Creator 是"创造 Skill 的元能力",Agent 自主完成知识转化(bootstrapping cycle)。Claude Code 的 `CLAUDE.md` 是同构机制。
- **睡眠学习(Sleep Consolidation)**:Claude Code 的记忆整理——双门控(距上次整理够久 + 积累够多新会话)触发**独立后台 sub-agent**,四阶段:**Orient → Gather → Consolidate → Prune & Index**;整理绝不在用户交互期运行;分布式锁防并发触发;失败自动回滚;**整理 sub-agent 的权限严格限定在记忆目录**。Hermes(Nous Research, 2026)将其常驻化:四层记忆(Prompt Memory / Session Retrieval FTS5 / Skill Library / Honcho 用户建模);触发固化条件具体化为">5 次工具调用、错误恢复、用户纠正、非显然工作流";偏好增量补丁而非整体重写。
- **系统提示自动优化(Karpathy "system prompt learning")**:LLM 像《Memento》主角,系统提示是它的笔记本;本质是用 edge case 磨锐规则边界。两条路线:**离线框架**(DSPy arXiv:2310.03714 / OPRO arXiv:2309.03409 / GEPA arXiv:2507.19457,GEPA 用自然语言反思 + Pareto frontier 进化提示,样本效率比 GRPO 高 1-2 个数量级)与**在线 diff 路线**(Coding Agent 读提示词文件、生成 code-level diff、人类专家终审)。实践上互补:先离线批优化,上线后 diff 路线持续演化(Experiment 8-3,tau-bench 航空客服,加负规则"never transfer due to a policy dispute")。
- **长任务跨会话续作**:Initializer Agent(跑一次,产出 `feature-list.json` + 初始化脚本 + 初始 commit + `progress.json`)+ Coding Agent(每会话一个迭代:从进度文件与 git log 恢复 → 实现下一项 → 跑测试 → 更新 `passes` → commit)。关键约束:**进度存在文件里而非上下文里**;结构化 JSON 优于 Markdown;全部 `passes: true` 才算完成。
- **从工具使用者到工具创造者**:预定义工具集的根本局限是"能力上限 = 人类工程师的预见"。**Alita(arXiv:2505.20286,"Minimal Predefinition, Maximal Self-Evolution")**:MCP Brainstorming → Web Agent 搜索开源库 → Manager Agent 读 README/代码 → 封装为 MCP 协议工具入库复用。从零写代码造工具时,**算力大头投在测试与验证**,用批量自动化测试吸收 Agent 在需求理解/边界条件上的不确定性。关键区分:**代码的归宿**——传统系统里代码一次性执行完即弃,自进化范式里代码成为可复用工具永久入库。
- **Voyager(NVIDIA, Minecraft)**:三要素=自动课程生成器(zone of proximal development)+ **技能库**(成功动作序列蒸馏为可执行代码,层级化可组合,"craft wooden pickaxe" 调用 "chop a tree")+ **迭代提示机制**(失败时把环境观察/报错/自验证结果折回提示词迭代改进)。3.3 倍独特物品发现。
- **能力积累三层次**:工具层(新工具可站在旧工具上形成层级)、知识层("哪个开源库适合哪类任务"的启发式规则)、策略层(自进化策略本身的元学习;稳定后可接力给 post-training 固化)。
- **安全边界(Safety Boundaries of Self-Evolution)**:①供应链攻击(自动下载恶意 PyPI/npm 包)→ 沙箱运行 + 新工具自动安全扫描;②能力漂移(capability drift)→ 工具类型白名单 + 库增长上限 + 定期人工审查;③工具质量退化 → 充分测试,错误工具被反复复用比一次性推理错误危害更大;④**记忆/经验投毒**(最内生攻击面:恶意注入内容沉淀为长期"经验",从一次性攻击变为跨会话持久攻击)→ 三层缓解:**写入前审查与来源标记(source tagging)、经验与指令的通道隔离(注入时明确"经验无指令效力")、检索时注入检测**;经验库须可溯源、可驱逐,知识新鲜度与防毒是一体两面。
- **Experiment 8-4(自进化流水线实操)**:基础工具只给 `web_search`/`read_webpage`/`code_interpreter`/`create_tool`/`search_tools` 五件,领域工具零预定义;流水线为 Search → Evaluate → Test → Encapsulate → Reuse;难点清单明确:搜索精度、文档理解、环境配置、错误恢复、**幻觉控制**(不得凭空假设库或 API 存在,必须基于真实检索结果)。工具复用需显式验证:同类任务再次执行时应直接取回已建工具,而非重走搜索创建流程。
- **Experiment 8-5(自进化评测集)**:20 个只说目标不提示工具名的跨域任务;四层验证——任务正确性、工具发现有效性、工具创建质量(LLM-as-a-Judge + Rubric)、工具复用能力(同类任务二次执行是否直接取回已建工具)。
- **载体形态的务实选择**:记忆与技能大多沉淀为文件系统上的 Markdown 而非手工设计的知识图谱——自然语言是模型最擅长的格式,叠加 LLM 做压缩与组织,构成不依赖人类先验结构、且随模型能力扩展的通用路径("对 Bitter Lesson  endorse 方向、对节奏务实")。
- **策略层与 post-training 的接力**:元经验短期沉淀在系统提示与 Skills 里,长期稳定后才考虑经强化学习固化进参数(Thought Question 7 进一步追问两条路径的边界:什么能力适合外置、什么适合写进权重)。

## 一致与相互印证

1. **"学习必须显式设计"直接支持上下文压缩子系统的存在性。** 该章论证无限 context 不会自动蒸馏、反而因 context rot 降低检索质量——这正是 §7 压缩策略(尤其 `summarize`:"花一次 LLM 调用把原始记录换成计算过的结论")和 `collapse_child`(子帧 transcript 折叠为返回值,§7.2)的理论背书。该章把 Chapter 2 的 context compression 明确归为"蒸馏的那一半",与我们 §7.2 中 summarize 强制保留"未完成事项/已确认事实/已做决定"的设计完全同构。
2. **prompt/code 双形态 Skill 的划分被该章的选型口诀印证。** "高频参数重的流程固化为代码;易变含策略判断的流程写成 Skill 文档"与 §2.1 的 `kind: prompt | code` 分工理由(确定性强适合纯逻辑)是同一个判断;Voyager 技能库"层级化可组合、新技能调用旧技能"印证了 §3.3 子技能伪工具 + §6.1 依赖图拓扑排序的价值。
3. **动态代码强制沙箱被供应链攻击分析强验证。** 该章指出自动搜索安装开源库是最直接的威胁,缓解即"沙箱运行 + 自动安全扫描"——对应 §9.2"动态代码永远走 SANDBOX,无配置项可关闭"与 §9.5 CodeScanner `pre:logic.exec` 否决。我们的默认值选对了。
4. **人工闸门被能力漂移分析验证。** "工具类型白名单 + 定期人工审查新工具"对应 §8.2 三层权限交集与 §5.4 HumanApproval(EXEC 级人工批准)。
5. **错误处理哲学一致。** Reflexion 的"失败排除一条路径,语言化反思带宽高于标量奖励"与 §3.2"工具失败作为错误观察写入帧上下文让 LLM 自行恢复"方向相同——我们都是把失败信息以自然语言还给模型,而不是丢弃或仅记标量。
6. **"进度在文件不在上下文"验证检查点与 blob 路线。** 长任务续作一节的关键约束(状态外置、结构化 JSON、崩溃零成本恢复)与 §13 M5 的"事件日志/检查点恢复(断电恢复演示)"、§8.4 blob store 按 run 落盘的设计互为印证;也与 §2.3"跨帧共享不开后门、显式走内核服务"的纪律一致。
7. **"代码的归宿"论点支持 Logic Kernel 的统一咽喉点定位。** 该章强调一次性执行与永久入库的分野;§9 把 code 技能与动态代码收敛到同一执行点、统一限额/信号/隔离,正是让"一次性代码"与"可复用代码"共享同一契约(§9.1 ExecRequest)——从一次性到入库只是注册动作,不是契约变化。
8. **按需加载(progressive disclosure)哲学一致。** 该章援引 Skills 的"元数据 → 核心流程 → 细节"渐进披露与 Hermes 技能库"默认只加载名称与摘要":技能再多也不一次性铺满上下文。§6.2 `visible_to` 只给可见技能生成伪工具 schema、SKILL.md 指令体在压栈时才进入帧上下文(§3.1 步骤 3),是同一原则在内核侧的结构化实现。
9. **版本共存支持"增量补丁"式演化。** Hermes 固化经验时"偏好增量补丁而非整体重写";§6.1 热重载的"新版本加载、新帧用新版、在跑帧钉住旧版(SO 库版本共存)"恰好为技能文件的频繁小幅演化提供了安全的运行期语义——演化不会打断在跑任务。

## 差距与可借鉴点

1. **最大结构性差距:内核没有"跨 Run 持久经验"的容身之处。** 该章全部机制的前提是学习成果比会话活得久;而 §2.4 明确 Run 是预算/权限/信号的作用域边界,blob store 也按 `blobs/<run_id>/` 隔离(§8.4),TraceRecorder 的 JSONL 只写不读。策略总结、失败反思、经验检索注入均无落点。黑板服务只是 §11.3 的预留扩展点和 §14 开放问题 4。**价值**:没有它,Skill/Tool 两个 Registry 永远只有"人写机器用"一个方向,自我进化的供给侧是断的。
2. **缺"运行期产物注册"路径。** §6.1 加载流水线的来源是本地目录/entry points,§8.3 工具来源是 decorator/entry point——都是进程外的静态供给。该章的工具生成流水线(搜索→评估→测试→封装 schema→注册→复用)要求注册表有写入 API。低成本近似其实已存在:Agent 用 `fs_write` 写技能包文件再触发 `reload()`(§6.1 热重载),但"生成产物该走什么校验与信任等级"没有答案。**价值**:这是把内核从"执行引擎"升级为"演化引擎"的最小切口。
3. **缺 PreAct 式"入库前验证门"。** 我们有逐帧 outputs schema 校验(§2.1),但没有"重置环境从头重放 + evaluator 确认任务真完成"的产物级验证。该章的教训具体而尖锐:步骤 100% 回放成功但任务实际没完成的坏程序会污染库,**没有验证门,自我改进循环必然腐坏**。**价值**:可直接复用 MockProvider 脚本化(§13)与 evaluator 概念,作为 Registry 写入路径的前置阶段。
4. **缺经验投毒防御,这是我们安全模型的盲区。** §5.4 的 ToolGuard/CodeScanner 防的是"执行什么",没人防"沉淀什么"。该章的三层缓解非常工程化可直接搬:①写入前审查 + source tagging(每条经验记录来源任务与来源内容);②**通道隔离**——检索到的经验以"参考资料"角色注入,显式声明无指令效力(这落在 §3.1 `build_request` 的消息构造上);③检索时轻量注入扫描,可疑条目降级或告警。**价值**:经验库一旦引入,这就是必选项而非增强项。
5. **缺蒸馏钩子。** run.finished / run.aborted 信号已存在(§5.1),但没有任何内置消费者做"事后花一次廉价 LLM 调用蒸馏本次运行"。该章给出明确的触发条件(Hermes:>5 次工具调用、错误恢复、用户纠正、非显然工作流)与入库标准(可迁移性)。**价值**:一个 ASYNC sidecar 即可起步,是接入成本最低的自我进化机制。
6. **睡眠整理可作为权限模型表达力的实证样例。** Claude Code 的"整理 sub-agent 权限严格限定记忆目录"在我们的模型里是自然表达:一个 code 技能,manifest `permissions.tools` 只放 fs 工具,RunConfig 再压上限,独立预算的后台 Run(§2.1/§2.4/§8.2)。双门控、分布式锁、后台调度属宿主职责,但内核侧还缺"定时/条件触发的后台 Run"这一概念。**价值**:四阶段(Orient/Gather/Consolidate/Prune)是一份现成的整理算法规格书。
7. **轨迹→code 技能编译(PreAct/工作流录制)是 TraceRecorder 的高价值下游。** §5.5 的 JSONL trace 已记录全部工具调用与帧树,具备编译数据源;"带验证谓词的状态机 + 谓词失败回退完整 Agent"本质是把 prompt 技能的动态决策降级为 code 技能的确定性执行——正好落在我们两种 Skill 形态的分界线上。**价值**:8.5–13 倍加速与成本骤降是可量化收益,且与 §9 Logic Kernel 的"执行即可仲裁资源"哲学一致。
8. **自进化能力评测方法(Experiment 8-5)。** 四层验证(任务正确性/发现有效性/创建质量/复用能力)与"任务描述不提示工具名"的防记忆设计,可作为 §13 集成锚点之外的第二根锚,尤其"工具复用能力"(同类任务二次执行直接取回)是回归测试的好断言。
9. **技能库增长的检索问题(Thought Question 2)对我们有前瞻性。** 该章自问:库变大后"检索正确的 Skill 本身成为难题,是否需要 Skill Retrieval Agent"。§6.2 `visible_to` 目前靠 manifest 白名单静态限定可见集,隐含假设可见技能很少;若支持运行期注册,可见集会膨胀,schema 注入成本与选择困难随之而来。**价值**:提前暴露 `visible_to` 的扩展性问题。
10. **知识新鲜度(knowledge freshness)无任何机制。** Thought Question 3 指出:"成功"的定义会随业务规则变化,过期经验不仅无用而且有害;该章把新鲜度与防毒并称"一体两面",要求经验库可溯源、可驱逐。我们的 blob store(§8.4)与 trace(§5.5)都没有 TTL、过期检测或驱逐概念——因为它们的定位是 run 内暂存,本不需要;但一旦 P3 的跨 Run 经验存储落地,新鲜度必须作为一等属性进契约(写入时间戳 + 来源 + 失效条件),否则经验库会随时间腐坏。**价值**:该章给出了明确的失效信号样例(工作流回放失败 → 标记"potentially outdated" → 回退重学),可直接借用。
11. **跨会话续作的结构化进度文件比我们 M5 检查点更激进。** §13 M5 的"事件日志/检查点恢复"恢复的是**同一 Run** 的执行状态;该章的 `feature-list.json` + `progress.json` + git log 恢复的是**跨 Run 的任务级进度**,且刻意用结构化 JSON 而非自然语言(模型读写更稳定),完成判据是全部 `passes: true` 而非"模型自述完成"。**价值**:这是检查点机制的应用层模式,但"完成判据外置为可机读状态"这一点值得写进示例——它能治"模型提前宣布完成"这一长任务常见病。

## 冲突或不同取舍

1. **自主生成 vs 静态治理。** 该章立场是"Minimal Predefinition, Maximal Self-Evolution"(Alita),Agent 自主搜索、创建、注册;我们 §6.1 的立场是加载期权限闸门 + 静态可分析依赖图,隐含"产物经人策划后才进入系统"。**评估**:不必然冲突——分水岭在**注册即信任**还是**注册即受审**。若规定运行期生成的产物默认按动态代码对待(强制 SANDBOX、CodeScanner 扫描、HumanApproval 批准注册、manifest 权限从严),则生成自由度与治理强度可兼得;若允许生成物直接获得与人写技能同等信任,则与 §8.2 三层权限模型的初衷相悖。该章自己的安全一节(人工审查、白名单)实际上站在我们一边。
2. **一次性执行 vs 永久入库的默认取向。** `python_exec`(§8.3/§9.4)定位为一次性"代码解释器",刻意不持久;该章认为持久化才是价值所在。**评估**:两者解决不同问题,不冲突——但需要一条从"一次性执行成功"到"封装注册为工具"的显式通道(见行动建议),否则该章指出的"经验随会话蒸发"在我们这里是默认行为。
3. **语义检索发现 vs 名字寻址。** 该章经验库/工具复用全部基于 embedding 语义检索;我们 §6.1 用 `<namespace>:<name>@<semver>` 精确寻址,模型经白名单拿到全量可见 schema。**评估**:精确寻址在受控可见集下更可靠(该章 Chapter 4 也承认裸字符串技能名不可靠,与我们 §3.3 伪工具判断一致);但库规模化后纯白名单不可持续,语义检索是补充而非替代。成立条件:可见技能数 < 几十时白名单优;之后需要检索层。
4. **离线框架优化(DSPy/OPRO/GEPA)vs 在线 diff 演化。** 该章对系统提示优化给了两条路线;我们内核与两者都不沾(提示词只是技能包里的文件)。**评估**:离线框架需要评测集驱动搜索,属应用/研究层,不进内核是正确取舍;在线 diff 路线(Coding Agent 改文件 + 人类终审)则可直接由现有原语组合(fs 工具 + HumanApproval + 热重载),值得作为示例而非内核机制。
5. **Voyager 课程生成器的主动探索。** 该章把"自动提出下一个探索目标"列为三要素之一;我们的内核完全被动(用户发起 Run)。**评估**:任务生成是应用层策略,内核只需保证 Run 可被程序化发起——当前形态已满足,无需改动。关联度低,仅记录。
6. **经验注入的作用域:全局系统提示 vs 帧级隔离。** 该章各机制(Experiment 8-1、Reflexion、Hermes Prompt Memory)默认把检索到的经验注入"那个 Agent"的系统提示,隐含单一全局上下文;我们 §2.3 是严格的帧隔离——经验若在根帧注入,子帧默认看不到,需要逐帧在 `build_request`(§3.1)时决定可见性。**评估**:我们的模型其实更细粒度、更安全(经验不会无差别泄漏进所有子帧,配合通道隔离可做到"哪个技能看到哪类经验"的显式清单),但代价是经验注入不能做成"一处注入全局生效"的便宜实现,必须与 manifest 白名单或帧策略挂钩。这是为隔离语义付出的合理成本,但要在 P3 的契约里写明注入作用域规则。

## 行动建议(按优先级)

**P1 — Registry 运行期写入路径 + 生成产物信任等级(影响 §6、§8、§9.2)**
- 为 Skill Registry / Tool Registry 定义 `register(artifact, provenance) -> Ref` 写入契约(§6.2/§8.3 扩展);v1 可用"Agent 经 fs_write 写技能包 + `reload()`"(§6.1)作为最小实现,但文档必须明确:**运行期生成的技能/工具默认不信任**——code 部分强制 SANDBOX 执行(§9.2)、经 CodeScanner 扫描(§9.5)、注册动作本身发信号并可被 HumanApproval 拦截(§5.4)。
- 理由:供给侧打通是自我进化的前提,且信任默认值必须在该章供应链攻击/能力漂移分析划定的边界内。

**P2 — 入库前验证门(影响 §6.1 加载流水线、§13 测试策略)**
- 在注册路径加 verify 阶段:重置环境重放(或用 MockProvider 脚本化重放)+ evaluator 通过才 publish。PreAct 原则直接写进设计:"程序性记忆需要验证门,否则自我改进循环腐坏"。
- 理由:成本极低(复用现有测试基建),防的是该章实证过的最坏失效模式(坏工具被反复复用,危害大于一次性推理错误)。

**P3 — 跨 Run 经验存储最小契约(影响 §11.3 services、§14 开放问题 4、§8.4)**
- 把黑板/记忆服务从开放问题提为正式(可最小)契约:append-only 经验条目,强制 source tagging(来源 run_id/任务/内容来源),支持按 tag 驱逐;检索结果经 `build_request`(§3.1)以独立"参考资料"消息注入,显式声明无指令效力(通道隔离)。
- 新鲜度作为一等属性随契约内建:每条经验带写入时间戳、来源、失效条件;失效信号借用该章样例(回放失败/被新事实推翻 → 标记 outdated → 驱逐或降级),对应差距第 10 条。
- 注入作用域规则写入契约:经验可见性按帧/manifest 声明,不做"一处注入全局生效"(对应冲突第 6 条)。
- 理由:这是策略总结、失败反思、睡眠整理三个机制的共同地基;通道隔离与可驱逐是该章给出的防毒底线,契约设计时一并内建比事后补强便宜得多。

**P4 — 蒸馏 sidecar 与失败反思钩子(影响 §5.4 内置 sidecar 表、§3.2)**
- 新增内置 ASYNC sidecar(订阅 `run.finished`/`run.aborted`):满足触发条件(参考 Hermes:工具调用数阈值、发生错误恢复、用户纠正)时,经 ProviderManager 调廉价模型蒸馏 strategy summary 或 failure reflection,写入 P3 的经验存储。
- 理由:纯增量、不动关键路径(ASYNC sidecar 永不拖垮 run,§5.3),是收益/成本比最高的自我进化起点。

**P5 — 睡眠整理样例技能(影响 §2.1/§8.2 验证、§14 新增开放问题"后台定时 Run 调度")**
- 把 Claude Code 四阶段(Orient/Gather/Consolidate/Prune & Index)实现为示例 code 技能:manifest 白名单限定记忆目录 fs 工具,独立 RunConfig 压预算上限。内核侧需补的仅是宿主可编程发起后台 Run 的说明,调度与双门控留宿主。
- 理由:既交付一个高价值样例,又反向验证三层权限模型对"受限自治代理"的表达力。

**P6 — 轨迹编译工具(影响 §5.4 TraceRecorder、§6)**
- 离线工具(不进内核):消费 TraceRecorder JSONL,把成功轨迹编译为带验证谓词的 code 技能草稿,走 P1/P2 的注册与验证路径。
- 理由:工作流录制/PreAct 的收益(8.5–13× 加速)有实证数字;编译产物天然落在我们 code 技能形态上,无需新抽象。优先级低于 P1–P3,因为依赖前两者存在。

**P7 — 评测锚点扩展(影响 §13 测试策略)**
- 在集成锚点中加入"复用断言":同类任务二次执行时,trace 中应出现已注册产物的直接调用而非重复生成(对应 Experiment 8-5 的工具复用层)。
- 理由:为 P1/P6 提供回归判据,成本一行断言。

**明确不纳入(关联度低或刻意排除)**
- Voyager 课程生成器、tau-bench 实验细节、DSPy/OPRO/GEPA 离线优化框架:应用/研究层内容,不影响内核契约;GEPA 的结论(语言化反思样本效率高)已间接体现在 P4 的设计依据中。
- MCP 双向宿主:维持 §14 非目标,但 P1 的注册契约应预留"产物 schema 可导出为 MCP 工具描述"的字段位置,供未来适配器使用(§8.3)。

**与里程碑的衔接(§13)**
- 不阻塞 M0–M4 既定 baseline;符合 §13"高级形态在 baseline 跑通后以替换注册项的方式进入,不动契约"的节奏:P1/P2 的 `register` 契约与验证门可在 M5 硬化期随沙箱一同落地,P4 蒸馏 sidecar 挂在 M4 信号体系之后,P3 经验存储作为 `agent_os.services` 扩展点的首个实现单独立项,P5/P6 以 examples/ 与离线工具形式交付。
- 若资源只允许做一项,做 P1(供给侧写入路径):其余所有自我进化机制都依赖它存在。
