## 章节内容概要

本章主题:实时约束让多模态问题变难的三类场景——**语音对话、Computer Use(GUI 操作)、机器人控制**。
明确划掉的边界:静态图像/文档理解已成熟不讲;多模态**生成**只是普通工具调用(第 5 章);连续视频流理解仍是开放问题。
贯穿全章的论点:三个场景都被"延迟 + 多模态"双重约束推向同一演化方向——从**串行流水线到端到端模型**;
并共享两条可迁移线索:**思考架构(快慢思考如何协作)** 与 **快慢接口(Latent Bridge)**。

### 语音架构三范式(沿"如何摆脱 VAD 轮流假设"展开)

**范式 1:Cascaded 级联(VAD → ASR → LLM → TTS)**

- 延迟账目:VAD 静音阈值 500–800ms;ASR 50–200ms;LLM TTFT 100–500ms(开推理 5–10s);TTS 200–500ms;全串行理想值 0.9–2s。
- 排队论放大:Total Latency ≈ Idle × 1/(1−Utilization);50% 利用率翻倍,80% 变 5 倍。
- **全链路流式化**(LiveKit Agents / Pipecat):ASR 边听边转、LLM 按句切片、TTS 句级流式,压到 600–800ms;
  但 VAD 静音等待是流水线启动前提,无法被重叠消除。
- **流式语音感知**(替代 VAD+ASR):能否流式取决于 **encoder 因果/分块 + 解码增量**(Whisper 卡在 encoder 需完整 30s);
  新路径是 LLM-based 听觉感知(Ultravox、Qwen2-Audio、Qwen2.5-Omni),合并"识别+理解",
  全上下文 ICL 改善专名识别,并继承 LLM 世界知识;轻量路径是给流式识别模型加 LoRA,
  **把话轮判断(turn detection)嵌入识别器**(Deepgram Flux、AssemblyAI Universal-Streaming),
  关键教训是训练标签的**"上帝视角"问题**——标注用了决策点后的音频,改用因果标注后模型犹疑消失。
- 模型输出**统一事件流**:文本 token + 声学事件标记 `<speak_start/end>`、`<interrupt>`、
  `<emotion:happy/frustrated>`、`<laugh>`、`<silence:500ms>` 等。
- 实验要点:PineClaw Voice API 电话 Agent(`make_phone_call` 工具进 ReAct loop,封装 IVR 导航/长时等待);
  Qwen2-Audio 分块模拟流式(非因果 encoder 需重编码全部历史,这是"模拟流式"与真流式的本质差别),
  增量延迟 100–200ms vs VAD+Whisper 的 800–1100ms,长停顿/噪声场景准确率明显更优。

**范式 2:End-to-End Omni(单模型听-想-说)**

- 收益:延迟更低、副语言信息经内部 latent space 直抵生成端;代价:数据需求大、可解释性差;**仍假设轮流**。
- **self-cascade(自级联)对照**:端到端的优势主要在**延迟**而非准确率;决定性能的不是中间表示(**bottleneck**)
  是否存在,而是**瓶颈携带什么信息**——中间文本升级为带副语言标记的结构化表示后,端到端优势常常收窄;
  且哪个更优可**按任务性质事先预测**(答案取决于语义内容 vs 取决于语气/情感/环境音)。
- 代表系统:OpenAI Realtime API(GA 后换专用 **gpt-realtime**,server 端 VAD、可打断、
  **异步 function call——等工具结果期间继续与用户说话**);Gemini Live(VAD 灵敏度可配);
  **Qwen3-Omni**(Thinker-Talker + MoE 保吞吐,Talker 多码本增量生成 + 因果 codec,冷启动首包约 234ms;
  注意 MoE 解决吞吐,首包延迟取决于生成侧架构);**Step-Audio 2**(原生音频端到端,感知副语言,
  集成 RAG 与工具,StepEval-Audio-Paralinguistic 83.09% 大幅领先)。

**范式 3:Full-Duplex 全双工(消解"轮流"本身)**

- **Moshi**(Kyutai, 2024):双音频流并行建模 + inner monologue 文本流,端到端约 200ms,打断成为自然行为。
- **TML Interaction Model**(2026):"交互性必须成为模型本身的一部分";**micro-turns** 约 200ms 粒度
  ("读 200ms、生成 200ms"),多模态流交错推进;TML-Interaction-Small(276B MoE/12B 激活)
  话轮切换约 0.40s(GPT-realtime-2.0 约 1.18s);慢思考做法:把**整段对话上下文**委托给后台强推理模型,
  结果增量流回,交互模型挑不打扰用户的时机织入对话。
- **GPT-Live**(2026):全双工生产化,每秒多次决策"说/听/停/打断/调工具";
  快慢分离——前台保场,后台委托 GPT-5.5(Instant/思考版分档)。
- 叙事收束:VAD 靠静音猜话轮 → 流式感知把判断升到语义层 → 全双工消解"切换"概念,barge-in 处理链在架构上消失。

### 思考架构三方案(实时响应 vs 深度思考)

- **方案 1:快思考出填充词 + 慢思考出答案(并行独立)**。快思考 500ms 托底,慢思考(test-time scaling)5–10s。
  失败模式:**简单问题过度思考**(已答"周三",8 秒后重复);**快慢结论不一致**(推理路径分叉、几秒内经自相矛盾,信任崩塌)。根因:两个无协调机制的独立过程。
- **方案 2:快思考管交互,慢思考当幕后参谋**。慢思考经 **Agent Status Bar**(该书第 2 章的动态元信息注入)
  向快思考递建议,能看到快思考输出,不再正面冲突。生产实例:GPT-Live delegation、Pine AI、
  Grok Voice "Think Fast"、TML。残余局限:**快思考可能误读状态条**;**慢思考中间推理对快思考不可见**
  (用户插话时只能凭有限理解作答);**无法"边说边想"**。工程理由:推理模型是"移动靶",解耦才能随时换最强脑。
- **方案 3:思考内化进单模型(Step-Audio R1)**。
  问题:**Textual Surrogate Reasoning**——模型"思考"时实际在分析文本转写而非声学特征,CoT 越长越差。
  **MGRD**(Modality-Grounded Reasoning Distillation):筛选提及具体声学参数("语速快 40%、音高变尖")
  的思考轨迹迭代自改进 + RL 防抄近路。**MPS 双脑架构**:Formulation Brain 持续思考产出思考段,
  Articulation Brain 逐段转成语音,流水线并行(t=200ms 首思考段 → t=350ms 首个音节)。
  实验:Speak-First(零延迟)Spoken-MQA 92.8% ≈ 完整 TBS 93.0%(CoT 开头多为复述题目)。
  产业分野:要随时换脑的赌方案 2,追求极致自然的赌方案 3。
- **快慢接口:Latent Bridge**。文本状态条是窄吸管;实时游戏场景中冻结快慢两模型、只训几千万参数的桥,
  把慢模型隐层结论投影为少量 **latent tokens** 拼进快模型输入,Atari 上比文本通道 +26%~+82%,每步仅加约 5ms。
  诚实边界:**任务瓶颈是"想不到"还是"反应不及"**决定快慢协作是否有效(相关性 r≈0.9)。

### 更像人的语音合成(执行层)

LLM 输出文本 + **控制 token**,把"在哪停、什么语气"交给主 LLM:`[THINKING]`、`[SEARCHING]`、
`[EMO:happy]`、`[SPEED:0.8x]`、`[SIGH]`、`[LAUGH:small]`、`[BREATH]`。
两条实现路径:自研 TTS 原生支持;或**语音克隆 + 参考音频库**(24 条 = 情绪×语速×风格,Fish Audio S1,数周上线)。

### Computer Use(GUI 自动化 Agent)

- **Perceive-Think-Act 循环**:截图 → 模型出思考+动作 → 执行 → 等响应再截图;三维度:Action Space、Visual Grounding、Model Architecture。
- Anthropic 三类工具:**GUI 操作**(mouse_move/click/type 12ms 间隔/key/scroll/screenshot/wait);
  **bash tool**(**持久会话**,120s 超时,**哨兵字符串判完成**,跨调用保持环境);
  **str_replace_editor**(view/create/replace/insert/undo,字符串匹配安全编辑,比整文件覆写不易误伤)。
- **视觉定位三路线**:**Set-of-Mark**(SAM/SEEM 分割 + 编号,选择题化,不依赖 DOM);
  **结构化元素索引**(browser-use:CDP 拿 DOM/Accessibility Tree,枚举可交互元素编号,不省 token 但准且稳);
  **纯坐标预测**(SeeClick、Claude;**分辨率强依赖**,训练用 XGA/WXGA/FWXGA,
  需**按长宽比选目标分辨率 + 双向坐标缩放**,否则坐标系统性偏移)。
  选型:有结构信息优先 DOM/无障碍树;Canvas/WebGL/游戏等没有时再视觉标注或坐标预测。
- **AOI(Agent–Computer Observation Interface)观察中间件**:**观察(连续/多模态)与动作(离散)解耦**,免重训。
  三门控组件:**关键帧捕获**(像素门跳近似帧 + 小模型判变化,静态屏幕近零成本);
  **音量门控语音转写**(有声才识别,Agent 第一次有"耳朵");
  **把帧旁白成持久文本**(最关键——原图清除后文本仍留内存)。
  结果:7B 到前沿 8 个模型 +17~48pp,语音任务差距最大;组件需**按模型选配**,过多图像 token 挤占推理反而掉分。
- **移动端**:动作空间换 AccessibilityService API + 手势语义;真正障碍是**生态壁垒**——
  Agent 绕过广告/注意力变现链,与平台商业模式结构性冲突,比验证码更难解。
- **实时性:未解的核心挑战**。OSWorld-Human 研究:步数远多于人类,**单步延迟随上下文变长递增**;
  "人类级准确率 ≠ 实用,效率才是真瓶颈";深层问题是无法"边执行边预判下一步"(thinking-while-operating)。
  已验证绕行方案:**快慢解耦 "Talking While Acting"**——小模型管实时语音,前沿 VLM 逐步操作浏览器,
  只经**极简纯文本契约(滚动状态摘要)**通信;**铁律:状态摘要确认完成前快模型绝不说"做完了"**;
  语音响应快约 15 倍(中位 0.58s vs 8.64s),成功率无损;**撤掉文本通道成功率归零**。

### 机器人控制

- **硬件不是瓶颈**(限视觉反馈类家务任务):XLeRobot 千元级双臂 + VR 遥操作,延迟 100–200ms;触觉/灵巧手仍是短板。
- **两层架构**:慢速 long-horizon planning(语义 + 任务分解,**Gemini Robotics-ER 1.5**,15 基准平均 62.8%)
  + 快速 **VLA 控制**(Vision-Language-Action);与语音快慢同构,但切分维度是"全局规划/实时执行",不同于 MPS 的"思考/表达"。
- **Action Chunking**(ACT 提出,π₀/OpenVLA-OFT 采用):VLA 单推理 1–10Hz vs 传统控制 50–1000Hz;
  一次推理生成 0.5–1s 动作块(50Hz 下 25–50 个动作),控制线程高频重放,模型异步生成下一块;
  **用反应性换平滑度**——块内对新视觉输入失明。
- **动作表示两路线**:RT-2/OpenVLA 离散 action tokens(Open X-Embodiment 20+ 平台预训练)vs
  **π₀ flow matching 连续轨迹生成**(扩散同源,精细操作更强)。
- **Sim2Real 两步骤**:**随机化范围标定**(从真实数据测摩擦/电机延迟分布,真机掉点逐步加宽)
  + **视觉对齐**(相机位姿标定 + 绿幕背景替换);实验 9-10 用 ManiSkill+PPO 零样本部署 SO100。
- 训练侧:VLA 主要靠模仿学习;RL 加成但"每任务单训"不泛化。

## 一致与相互印证

1. **特权操作执行前可拦截,被章末 Q9 独立背书。** 书中三场景的共同隐忧是"快思考动作造成不可逆后果";
   我们的答案是 `pre:tool.call` SYNC 否决(§5.1)、READ<WRITE<NET<EXEC 三层权限交集(§8.2)、
   HumanApproval 人工闸门(§5.4)、`idempotent` 标志(§2.2)。本章从需求侧证明这不是过度设计:
   越是低延迟路径越需要同步仲裁点,也顺带支持 §5.3 fail-closed 默认与 §9.5 `pre:logic.exec` 否决。
2. **"换脑不换壳"印证 Provider 分层。** 方案 2 成为主流的理由是"推理模型是移动靶,交互层稳定、大脑可插拔",
   与 §4.2 ProviderManager 的模型路由(`model.prefer`)+ fallback 链同构,支持 §1 公理 2"子系统互不相识"。
3. **self-cascade"瓶颈信息论"支持 outputs schema 与子帧折叠。** 实验证明"瓶颈携带的信息决定性能,
   裸文本最差;结构化带标记的中间表示可追平端到端"——§2.1 返回值 schema 校验、§2.3 `working`
   结构化暂存且压缩优先保留,是同一方向的正确赌注。
4. **AOI"旁白成持久文本"印证压缩策略的信息观。** 8 个模型 +17~48pp 的关键是"文本持久化"而非选帧算法,
   与 §7.2 `summarize` 强制保留"未完成事项/已确认事实/已做决定"、`spill` 只留 `{ref, preview}` 同构,
   可视为 §7.3 不变量体系在多模态场景的独立实验验证。
5. **"交互性内建于模型"反向印证内核边界。** 全双工、打断、micro-turns 是模型内部能力,
   编排内核只需把交互模型当 Provider 接入,不必把流式话轮管理做进内核——
   支持 §14 非目标划法:Agent OS 的步进 loop 服务编排粒度,不是 200ms 交互粒度。
6. **延迟随上下文增长(OSWorld-Human)给压缩子系统补了第二条存在理由。** §7 的动机原是防溢出与成本;
   本章补充:上下文变长单调拖慢每步决策,压缩同时也是延迟控制手段。
7. **"上帝视角标签"教训与 sidecar 因果性契合。** 书的原则:用"决策点之后才出现的信息"做的判断线上必败。
   我们的 LoopDetector(§5.4 滑窗签名)等只依据已发生信号,天然满足;此原则应作为未来
   "预判型机制"(投机执行、提前压缩)的设计约束。

## 差距与可借鉴点

1. **缺"后台帧 + 状态通道"并发拓扑(最重要差距)。** 我们的调用语义严格同步:父帧 await 子帧,
   transcript 折叠为单个返回值(§2.3、§3.1)。方案 2 / GPT-Live delegation / Talking While Acting 共同要求:
   父帧继续运行、子帧后台跑、子帧滚动发布状态摘要、父帧按需读取、**确认完成前不得宣称完成**。
   `parallel_invoke`(§3.4)在 join 点前父帧同样无法行动;黑板只有预留(§11.3),§14#4 未解。
   "撤掉文本通道成功率归零"是这条通道价值的硬实验证据,也直接回答 §14#4 的现实需求。
2. **内核 loop 不消费流式响应,无"挂起工具"语义。** §3.1 只用 `chat()` 等完整响应;
   书中全链路流式化与 gpt-realtime 异步 function call 都依赖增量消费与"调用已发起、结果稍后回填"。
   差距具体化:无 chunk 级信号、无工具挂起语义、trace 无 chunk 记录格式。
3. **token 估算与压缩不覆盖多模态。** §7.5 char/4 粗估对图像/音频 token 失效(一张截图可达上千 token);
   `supports_vision` 已在 §4.1 caps,压缩侧无对应口径。AOI 给出可直接借用的策略:
   **图像先旁白成一句文本再逐出**(多模态版 spill/summarize);"组件按模型选配"提示压缩策略需读 Provider caps。
4. **工具级工程细节可照搬(§8.3–8.4)。** (a) `shell_exec` 升级为**持久会话 + 哨兵判完成 + 可配超时**,
   跨调用保持 cwd/env;(b) 加 **str_replace_editor 式安全编辑**(view/create/replace/insert/undo),
   比 `fs_write` 整覆写不易误伤且便于审计;(c) computer-use 工具的**按长宽比选分辨率 + 双向坐标缩放**
   归一化层,属工具实现,值得写成 examples 参考。
5. **输入侧门控(AOI 像素门/音量门)。** 我们的成本控制全在执行后(§4.2 记账、BudgetGuard);
   对持续感知型技能(监控屏幕、听会议),"廉价前置门 + 有意义变化才进上下文"能把感知成本压到近零,
   与 §7.5"驱逐时改道"hook 同构。
6. **排队论容量口径。** §4.2 令牌桶若把 provider 利用率顶过 80%,尾延迟非线性爆炸;
   目前 Usage 只有成本/步数维度(§2.4),缺利用率视角。优先级低,对服务化形态(§11.3)有参考价值。
7. **控制 token 输出约定。** 若未来支持语音技能,这是 prompt 技能指令体(§2.1 entry)层面的约定,
   不需内核改动;但"指令体约定结构化输出标记、由下游工具消费"是通用模式,与 §3.3 伪工具呼应。

## 冲突或不同取舍

1. **默认串行 vs 全面并发。** §3.4"默认串行"与本章"一切实时场景靠快慢并行"相反。各自成立条件:
   批量文本任务中串行使预算按帧归集(§2.4)、错误沿栈上抛(§3.2)、SYNC sidecar 确定性(§5.3)都简单可靠;
   延迟敏感场景中 15 倍延迟差距(0.58s vs 8.64s)表明串行不可接受。结论:不是谁取代谁,
   我们的并发原语需从 fork/join 扩到"后台帧 + 状态通道"。
2. **子帧 transcript 完全折叠 vs 中间推理可见性需求。** §2.3 隔离是最便宜的分层压缩;
   方案 2 的局限恰是"慢思考中间结论不可见"。书的答案不是取消隔离,而是开一条窄的显式边通道——
   与 §2.3"不开后门、显式走内核服务"一致:"折叠默认 + 黑板预留"组合正是该权衡的正解,只是黑板未定规约。
3. **同步分发阻塞 loop vs 异步 function call。** §3.1 第 6 步 await 工具完成才进下一轮;
   gpt-realtime 边等边聊。前者对调试/trace 友好(每步因果链完整),后者只对实时交互必要。
   评估:应作为 runner 可选模式而非默认,否则动摇 trace 简单性。
4. **步进检查点 vs 无话轮连续流。** 全双工主张"打断不应是需要特殊处理的事件";我们的 `pre:step` 假设离散步。
   非真冲突:全双工在模型内部(Provider 之后),我们的步是编排粒度;需在文档写明边界,
   避免有人用 sidecar 实现话轮管理——那是 Provider 的职责。
5. **端到端 vs 模块化的可观测性。** Q1 指出端到端出错比级联难调试。我们站在模块化一侧(TraceRecorder,§5.4);
   未来接入端到端交互模型时它对内核是黑盒,trace 粒度上限由 Provider 决定——
   可在 §4.1 契约预留"Provider 内部事件透传"字段(把话轮决策事件转发到信号总线)。
6. **思考内化(方案 3)vs 分层哲学。** MPS 把思考与表达绑进同一模型;我们是"内核拥有循环,Skill 拥有策略"。
   不冲突(方案 3 对我们仍是 Provider),但提示长期风险:模型内化越多编排能力,
   内核价值越向"仲裁/审计/权限"集中——这正是 §1 公理 3"一切特权操作可拦截"的护城河,方向上安全。

## 行动建议

按优先级排列(P0 最高):

1. **【P0|§11.3、§7.3 扩展点、§14#4;Sidecars/内核服务】**把黑板从"预留"升级为有规约的内核服务
   **StatusBoard**:按 run_id 作用域的 KV(append-only + 最新值视图),读写全走信号,
   权限并入 manifest 白名单(正面回答开放问题 4);runner 支持"子帧每步把进度摘要写入 board"。
   依据:"纯文本契约撤销则成功率归零"。
2. **【P0|§3.4、§2.1;Kernel Runner】**增加**后台帧**并发拓扑:`parallel_invoke` 之外提供
   `spawn(skill, input)`——子帧独立预算记账、不阻塞父帧,父帧经 StatusBoard 读滚动状态,
   join 退化为读终态;后台帧仍是帧树节点,调用栈语义不动。配套可选 outputs 校验 hook:
   **父帧读到子帧终态为完成前,拒绝输出"已完成"类结论**("绝不说 done"铁律)。
   这是方案 2 / GPT-Live delegation / Talking While Acting 三模式在我们抽象上的统一表达。
3. **【P1|§3.1、§4.1、§5.1;Providers / Runner / Sidecars】**runner 可选消费 `stream()`:
   新增 `post:llm.chunk` 信号(仅 ASYNC),允许工具调用在流中提前解析发起;
   定义"异步工具"挂起语义(结果以观察形式后续回填帧上下文);TraceRecorder 记录 chunk 序列(M4 扩展)。
4. **【P1|§7.2、§7.5;Context Compression】**多模态 token 口径与**旁白式压缩**:估算器加按模态计数
   (图像/音频 token 取自 provider usage 或按分辨率公式);新增 `narrate` 策略——逐出多模态消息前
   经 ProviderManager 生成一句文本旁白留置(AOI 第三组件的压缩化),作为"驱逐时改道"hook
   挂在 RollingWindowCompressor 基座上;压缩策略可读取 Provider caps 按模型调图像 token 预算。
   并在 §7 职责补一句:压缩兼负延迟控制。
5. **【P2|§8.3、§8.4;Tool Registry】**`shell_exec` 加持久会话 + 哨兵判完成 + 可配超时;
   新增 `str_replace_editor` 式安全编辑工具;examples/ 提供 computer-use 参考工具集
   (按长宽比选分辨率 + 双向坐标缩放、DOM/SoM 双路定位),明确属工具实现而非内核职责。
6. **【P2|§5、§7 文档;Sidecars / Compression】**把 AOI 像素门/音量门抽象为**"感知门"模式**写入文档:
   廉价前置判断 + 有意义事件才入帧上下文,作为自定义 sidecar/工具参考模式,不进 baseline。
7. **【P3|§4、§14;Providers / 开放问题】**写明实时交互边界:全双工/Omni 模型作为 Provider 接入
   (§4.1 caps 加实时能力位,预留"内部事件透传"字段);内核不实现话轮管理与打断;
   技能编写指南收录"控制 token 输出约定"模式。

总体判断:本章与 Agent OS 直接重叠面中等,但不宜视为"关联度低"而略过——
三条可迁移原则(快慢解耦并发拓扑、状态边通道承重、瓶颈信息论)都指向我们最薄弱的两处:
并发语义与黑板服务。建议 P0 两项优先落地规约,P1 作为 M5 后子系统增量,P2/P3 进入文档与 examples。
