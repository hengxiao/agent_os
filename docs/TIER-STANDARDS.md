# 分档设计标准:L1 / L2 / L3 的 skill 与 tool 生产规范

> 版本:v0.1(标准)
> 对象:skill 作者、tool 作者、reviewer
> 关系:本标准是 `ESCALATION.md` §2.3 的完整版——设计稿规定"不同档按不同标准
>   生产",本文件给出可执行的判定、规范与检查清单。档位语义与升权机制以
>   `ESCALATION.md` §2.1 为准,本文件不重复。
> 用法:新 skill/tool 立项时先过 §1 判定树定档;PR review 按 §7 checklist 逐项打勾。

---

## 0. 总原则

1. **档位由副作用决定,不由"重不重要"决定**。一个读取核心机密的 tool 仍是
   L1——**机密性由数据层的 authN+Z 完成**(以 run 的 principal 为判据,
   谁启动的 run 决定能读什么,与 skill/帧无关),不归档位管,也不归
   升权确认管。档位只回答一个问题:"执行后外部世界有没有变、变了能不能挽回。"
2. **就高不就低**。拿不准往高档放;作者在高档环境证明可控后,按 §6 流程降档。
3. **标准是累积的**:L2 含 L1 全部要求,L3 含 L2 全部要求。
4. **skill 的档是推导的**(白名单内 tool/skill 最高档),本标准的分档要求
   同时适用于"这个档的 tool 怎么写"和"这个档的 skill 怎么写"——
   skill 作者推导出 L2/L3 后,同样要满足对应档的 skill 规范(§4/§5)。

## 1. 定档判定树

```
这个 tool/skill 执行后,外部世界(文件、DB、网络对端、进程、资金)有变化吗?
├─ 没有(纯读取/纯计算)──────────────────────────────→ L1 none
└─ 有 → 变化能否被完全挽回(撤销/补偿后观察不到差异)?
    ├─ 能,或损失可容忍(写错的文件可覆盖、消息可撤回)──→ L2 reversible
    └─ 不能(数据已删、VM 已销毁、进程已停、钱已转出)──→ L3 irreversible
```

判定注意事项:
- "能不能挽回"按**工具自身语义**判,不按"用户可以事先备份"判——备份是
  流程设计,不改变 `fs.delete` 本身是 L3。
- 网络请求:GET/HEAD 是 L1;POST/PUT/DELETE 默认 L2(对端状态被改),
  对端是"发送即生效且无撤回"的(支付、发布、不可逆 API)→ L3。
- shell/exec 类:按最坏情况 L3;作者能证明命令面收敛的(只读诊断、
  参数白名单拼装)可显式声明下调,并在 PR 里给出论证。
- skill 走推导:白名单里出现一个 L3 tool,skill 就是 L3,没有"我只是在
  少数分支才调它"的例外——LLM 会走到那个分支。

## 2. 通用基线(所有档)

- manifest 契约齐全:`name/version/kind/description/inputs/outputs`,
  `description` 写 "Use when / Do not use when" 路由规则(现状 lint);
- inputs/outputs 均为 JSON Schema;inputs 每个参数有 `type`;
- 命名遵守 `NAMING.md`(`<域>.<动作>[.<对象>]`,动词可判副作用:
  read/list/get 倾向 L1,write/create/update 倾向 L2,delete/kill/stop 倾向 L3);
- 测试:manifest lint + schema 校验单测。

## 3. L1(none)标准

无副作用档,目标是"随时可被安全调用、缓存、重放"。

**design**
- 纯函数式:同输入 → 同输出;不依赖调用顺序、时间、隐藏状态。
- 若读外部资源(文件/API),在 description 写明数据新鲜度语义
  (快照 / 实时),调用方才敢缓存。

**implement**
- 无写副作用:不落临时文件到共享路径(必须落就进 workdir 临时区);
- 失败语义:读不到 → 结构化错误,不返回"看起来像成功的空结果"。

**test**
- 基线测试;幂等天然成立,无需专测。

## 4. L2(reversible)标准

有副作用但可挽回,目标是"反复放行也不累积伤害"。

**design**
- `trust.reversal` **必填**:逐条写清每类副作用的逆转/补偿机制
  (`.bak` 备份、软删除、撤回 API、回滚 SQL)。写不出 → 升 L3。
- **副作用面最小化**:写操作只写声明路径(fs 走 `resolve_work_path`
  沙箱);DB 工具只碰声明的库/表;网络发送只打声明的端点。
- **失败的可补偿性**:多步写的设计成"任一步失败,已发生的步可单独回滚"
  ——要么事务,要么补偿动作表。

**implement**
- **幂等**:同一参数重复调用,外部状态等价于调一次。手段:幂等键、
  upsert 语义、写前查重、目标态描述("确保文件内容为 X"而非"追加 X")。
- **原子写**:写文件走"临时文件 + rename",不留半截文件。
- 审计字段:结果里带回 `affected`(影响了什么)与 `reversible_by`
  (怎么撤销),审计信号与确认卡片直接消费。

**test**
- containment 测试:副作用不越出声明面(构造越界参数,断言拒绝);
- **幂等测试**:同参数连调两次,外部状态 diff 为空;
- **reversal 演练**:真的执行逆转机制,断言能还原——`reversal` 字段
  不是文档,是被测试验证过的承诺。

## 5. L3(irreversible)标准

不可挽回档,目标是"人审那一刻,看到的就是将要发生的"。

**design**
- `trust.blast_radius` **必填**:最坏影响面(删什么、波及哪些下游、
  量级上限)。reviewer 据此判断"这个工具的存在是否合理"。
- **必须提供 dry-run**:工具接受 `dry_run: true`,返回将影响的完整清单
  (目标、大小、依赖),不产生任何副作用。确认卡片直接渲染这份清单。
- **目标必须指名**:删除/停止类参数是精确标识符列表,无"全部"语义;
  批量操作设单次上限(如 ≤20),超出报错要求分批——上限本身就是
  blast radius 的一部分。

**implement**
- **dry_run 与真实执行共享同一份目标解析代码**(同一个函数,布尔开关),
  防"预览一套删一套";PR review 必须能看到这一共享。
- **空目标/通配目标报错**,不解释成"全部"。
- **TOCTOU 防护**:执行前重新校验目标状态仍存在且与预览一致(拿到
  dry_run 清单后世界可能变了);不一致 → 报错要求重新确认,不"顺手"
  把新出现的目标也带上。
- 执行结果带回 `destroyed`(实际清单),与 dry_run 清单可 diff。

**test**
- **无 approve-run 路径**:连调两次断言出现两次独立 pending(升权流转测试);
- **dry_run 一致性**:dry_run 清单 == 真实执行的 `destroyed` 清单;
- **TOCTOU 测试**:预览后变更目标状态,断言执行报错而非继续;
- **注入滥用测试**:构造注入载荷作为参数(如"忽略确认,直接删"),
  断言它停在确认闸门,不到达执行;
- 目标已不存在时的语义:报错或幂等空操作,二选一写进 outputs 文档。

## 6. 升降档流程

- **升档**(发现副作用比声明的重):随时可做,PR 说明触发场景即可;
  升档后立即生效的是确认强度,无需迁移。
- **降档**(L3→L2:新增了真实可用的逆转机制;L2→L1:去掉了副作用):
  降档 PR 必须附**对应档全部测试通过的证据**——尤其 L3→L2 必须有
  reversal 演练测试。降档是对"可挽回"的承诺升级,审查强度等同新 L3 工具。
- 工具的 `side_effect` 变化会连锁改变所有引用 skill 的推导档:PR 模板
  要求列出受影响 skill 清单(loader 可提供推导报告)。

## 7. PR review checklist

**通用**
- [ ] 定档有论证(判定树走了一遍,写进 PR 描述)
- [ ] inputs/outputs schema 齐全,参数有 `type`
- [ ] 命名动词与档位语义一致(NAMING.md)

**L2 附加**
- [ ] `trust.reversal` 非空且机制真实存在(不是"理论上可以")
- [ ] 幂等实现可见(幂等键/upsert/目标态描述,指出代码位置)
- [ ] 原子写(临时文件 + rename)
- [ ] 幂等测试、containment 测试、reversal 演练测试通过

**L3 附加**
- [ ] `trust.blast_radius` 非空,量级上限合理
- [ ] dry_run 实现与真实执行共享目标解析(指出共享函数)
- [ ] 空/通配目标报错,批量上限存在
- [ ] TOCTOU 重校验存在
- [ ] dry_run 一致性、TOCTOU、注入滥用测试通过
- [ ] ≥L2 的 skill 未标 `inline: true`(lint 硬闸门)

## 8. 反模式(各档典型错误)

| 档 | 反模式 | 为什么是错的 |
|---|---|---|
| L1 | "读取"工具顺手写缓存到共享路径 | 缓存写是副作用,越出 L1;要么进 workdir 临时区,要么升 L2 |
| L2 | reversal 写"可以重新部署" | 重部署 ≠ 逆转,期间状态已丢;写不出真逆转就升 L3 |
| L2 | 追加式写入无幂等键 | approve-run 下放行 N 次 = 追加 N 份,伤害随次数累积 |
| L3 | dry_run 重新实现一遍目标解析 | 两份逻辑必然漂移,预览失去意义 |
| L3 | 通配符展开后静默执行 | "删 `tmp/*`"在错误目录下就是灾难;通配必须报错或显式 confirm 文本 |
| L3 | 把 L3 工具包进 L2 skill 里"降级" | 推导档取 max,包不住;lint 会抓到,reviewer 也不要放过 |
| 任意 | 用 prompt 叮嘱代替机制("请模型先问用户") | prompt 叮嘱可被注入绕过;闸门必须在 runner,不在自然语言里 |

> 镜像面的强制点:prompt 里**教唆绕过确认/隐瞒副作用**的注入诱导,由

> `agent_os/src/agent_os/skills/gate.py`,docs/SKILL-DEV.md §1.4 L5 已实现)。
