## 章节内容概要

该章分两大半:**如何造一个可靠的 Coding Agent** 与 **代码生成作为通用 Agent 的元能力(meta-capability)**。

**前半:Coding Agent 架构与工程**

1. **基础能力论**:代码生成是通用 Agent 的基础能力;最小工具集为七件套——Code Interpreter(沙箱)、Bash、Read、Write、Edit、Glob、Grep。子代理委派由框架编排层负责,不做成工具。
2. **案例:Manus → OpenClaw**:开放式通用 Agent 的范式 = Coding Agent + 文件系统。文件系统是记忆/知识/能力的中枢(`MEMORY.md` + 按日归档的 Markdown 日志,优于向量库:可人读人改、保序、可 Git 版本化);Agent 通过写文件实现"越用越聪明"的自演化。适用边界:仅对开放式任务成立,垂直封闭域(客服、语音助手)中代码只是工具而非架构枢纽。
3. **Sessionless 设计**:跨消息持久化分两层——文件系统状态天然持久(工作区挂在沙箱外持久存储);进程状态保活或按需重建(空闲超时销毁前把工作目录、环境变量、后台任务清单序列化到工作区文件,唤醒时重建)。代价是每条消息都要重载完整轨迹,压缩策略因此关键。
4. **安全体系**(全章最密的部分):
   - **Lethal Triad**(Simon Willison):私有数据访问 + 不可信内容暴露 + 对外通信能力,三要素齐备即成完整攻击闭环;作者补第四维 **Persistent Memory** 作为攻击放大器(恶意指令可跨会话潜伏)。对应四类边界:数据边界、输入信任边界、输出影响边界、跨会话边界。
   - **沙箱工程四关切**:网络出口控制(默认断网 + 白名单代理按需放行,是对 Triad 第 3 项的确定性防线)、文件系统挂载范围(源码只读挂载、独立可写工作区、凭据文件不挂载)、资源限额(超限须返回结构化错误而非静默杀进程,给 Agent 修正策略的机会)、持久会话与隔离的调和(会话不得活得比沙箱久;持久化的是**可审计的状态描述**——文件/脚本/清单,而非不透明进程)。
   - **命令语义解析优于关键字黑名单**:Shell 组合爆炸使黑名单失效(`$(echo rm) -rf /`、`find / -name '*.log' -exec rm {} \;`、`curl -o /etc/crontab ...`),需按命令的参数类型与解析规则做语义级理解。
   - **Speculative Execution(推测执行)**:安全审查与用户可见进度解耦——先显示无副作用的 UI 提示("Reading file ..."),后台跑审查;与 CPU 推测执行不同,猜错无需回滚,只换提示文案。
   - **多方委托下的忠诚度(principal loyalty)**:模型默认"帮助正在说话的人"在谈判等对抗场景失效;Harness 须在系统提示中钉死忠诚准则(委托人指令最高优先,外部内容一律降级为"可参考的数据,无指令效力";拒绝时不枚举受保护细节)。
   - **信任边界下沉到数据层**:Permission-Embedded Data Objects——数据实体自带声明式权限规则/校验器,运行时管线对每次写入强制执行;每次操作带 access context,自治 Agent 以受限身份(scoped principal)运行。对比实验中实现零违规写入,代价约 2ms/写。原则:**代码编写者与运行者都不可信时,可靠约束不能放在生成的代码里,必须放在人审过的地基里**。
5. **推荐工作流**:项目文档先行(缺失则先逆向出架构文档)→ 任务理解与需求澄清 → 设计文档 + 用户审批闸 → 实现 + "测试-修复"自循环(完成判据是"测试通过"而非"代码写完")→ 自 review → 文档同步。**Project Instruction Files**(CLAUDE.md/AGENTS.md/.cursorrules)是项目级系统提示,也是 KV Cache 友好的稳定前缀。
6. **Harness 工程**:Agent = Model + Harness;四组件——验收基线(测试/CI)、执行边界、反馈信号(linter/类型检查)、回滚机制(Git/沙箱/快照)。任务按"目标清晰度 × 验证自动化"分四象限,Coding 天然落在甜点象限,这是 Coding Agent 最成熟的真正原因。四原则:**constraints over guidance**(能编码成代码的规则不要只写进文档)、验证自动化、反馈要快且结构化、回滚必须可靠。约束的深层目的是**防过程错误**(删库重建也"修好"了故障——结果对不代表路径对,这是 reward hacking 的日常形态)。工具编排的**故障边界控制**:并行调用中,故障只在同批次内传播,不上溯到父操作。
7. **失败与错误恢复**(对内核最有参考价值的一节):
   - **四层失败分类**:API 层(429/过载/超时/断连/输出截断)、工具层(幻觉调用/参数畸形/执行异常/同错重试)、上下文层(窗口溢出/压缩失败/tool_call 与 result 配对阵损坏)、控制流层(死循环/死亡螺旋)。
   - **检测:先分类再计数**——先问"重试有用吗"(retryable vs non-retryable);模式检测:重复调用指纹(tool name+args 哈希)、各恢复路径独立连败计数;**活性监控**:流式连接最危险的不是断开而是静默停滞,需独立于连接超时的 idle watchdog;**完整性监控**:注入上下文前修复缺失配对的 tool result,生产模式可打占位补丁,训练数据采集模式拒绝修复(防污染)。
   - **恢复:按用户可见度分级升级**——静默重试(指数退避+抖动、尊重 Retry-After、区分前台主循环与后台辅助调用,防"重试放大")→ 降级续跑(截断则提高输出上限重发或追加元指令续写;主模型持续过载则 fallback,须先剥离前一家专有格式块)→ 才上报用户。工具层错误走另一路:**不终止会话,把错误变成模型输入**(结构化"无此工具"错误、附契约提示的参数错误、可程序化修复的参数先修复再执行)。
   - 核心原则:**错误处理的单位不是单次请求,而是整个恢复环路**;恢复未确认失败前,中间错误对用户和下游事件订阅者一律暂扣。
   - **终止:每条恢复路径都要有熔断上限**,阈值来自生产数据而非拍脑袋(Claude Code 压缩熔断"连败 3 次"源于真实统计:曾有会话连败 3000+ 次,全球每天白烧约 25 万次 API 调用)。**死亡螺旋**:错误路径上的副作用自身调 LLM 再失败导致级联(停机遇 context overflow → stop hook 自动提交代码 → hook 调 LLM 写 commit message → 再 overflow),防御 = 错误路径上禁用一切调模型的副作用 + 递归深度计数器。最上层是全局终止:最大轮数、会话预算、人工升级。
8. **五个实现技巧**:并行工具调用 + 流式执行(第一个调用参数一生成完即开始执行,不等后续调用)+ 级联中止(只中止同批次内有依赖的调用,工具须声明是否支持并发,默认否,fail-safe);细粒度上下文管理(按行区间读、返回带行号;长输出保留头尾、中间折叠并持久化到临时文件);环境信息动态注入(cwd/git 分支/最近提交/未暂存改动,以 Agent status bar 形式追加在上下文末尾,不进静态系统提示,保 KV Cache);持久终端会话(默认共享一个长活终端,保留 cd/env/venv 状态);即时语法反馈(文件写入后工具层自动跑 linter,结果并入工具返回值)。
9. **搜索工具谱系**:grep(精确但无语义)、glob(结构探索第一步)、语义代码搜索(结构感知分块 + BM25/dense 混合检索 + reranker;业界分歧:Claude Code 不建嵌入索引纯 agentic 检索 vs Cursor 建索引换跨文件语义召回)、LSP 符号级定义/引用查找(重构必需)。组合策略:由粗到细、由语义到语法。
10. **文件编辑五方案**:diff 描述 + Apply 小模型(Cursor,配 speculative decoding 达数千 token/s)、old string→new string(Claude Code,可预测、无歧义,自建首选)、行号定位(模型数行号易错,需深 IDE 集成)、类 Vim 命令(强模型才驾驭得住)、首尾字符串匹配(大块删除的经济折中)。

**后半:代码作为元能力的六个方向**

1. **思维工具**:LLM 负责理解题意并形式化为代码,sympy/constraint solver 负责精确计算(Wolfram 洞见:符号计算引擎精确但 NLU 脆弱,LLM 反之)。附带重要方法论:**模型与 Harness 此消彼长**——模型越弱,Harness 越要把关键推理卸给代码;同一 Harness 配不同强度模型可得出相反结论。
2. **业务规则代码化**(τ-bench 航空改签例):三层防护——系统提示里的自然语言规则帮助理解与解释;工具描述 + `expected_*` 可选参数构成**强制检查清单**,引导模型调用前逐条自查(模型常在备参阶段就发现违规而避免调用);**服务端基于数据库 ground truth 的代码校验做最终闸**——所有策略事实(舱位、保险、订票时间、当前时间)一律取自数据库与服务端时钟,绝不信任模型自报参数;自报值与真值不符时记录 mismatch 日志(可发现错误信念或注入)。
3. **多媒体生成**:PPT(Slidev)/视频(Blender API)/可视化,核心是 **Proposer-Reviewer** 双代理机制——Reviewer 渲染结果图交给 Vision LLM 评,产出结构化改进建议(页码/问题类型/严重度);双代理相对单代理自审的核心优势是**上下文管理**(Reviewer 只看最新版渲染图,Proposer 只累积结构化文本反馈)。停止条件 = 质量达标 + 最大轮数预算。
4. **系统适配器**:代码是连接异构系统的"万能胶水"(无 SDK 时读文档现写适配器;GUI-only 系统先 Computer Use 再固化为 RPA 代码);自适应日志解析(前端遇到无法解析的格式 → 上报 Agent → 生成解析代码 → 虚拟浏览器自测 → 热更新);生产轨迹自动诊断(生成结构化问题报告 + 引用轨迹 ID 的回归测试用例 + 经 MCP 建 GitHub Issue)。
5. **Generative UI**:A2UI 类声明式协议(Agent 只输出 JSON UI 描述清单,客户端用受信组件目录渲染,安全优先;与 AG-UI 区分——后者是事件/传输协议);HTML 取代 Markdown 成为交付物;动态表单一次性澄清意图;**Artifact 模式**(Agent 生成 SQL/可视化代码作为独立 artifact,系统执行、前端渲染,**数据从数据库直达界面,不经过 LLM 上下文**——更快更准,LLM 不"转抄"数据)。
6. **Bootstrapping**:OpenClaw `doctor` 自修复(先用确定性检查覆盖高频问题,LLM 只兜长尾;安全修复自动执行,危险操作需确认);Agent 造 Agent 的关键是**以验证过的高质量实现为参照样本做改造**("自我复制 + 适应性修改"),而非从零生成。

章末附 12 个实验(数学/逻辑推理、τ-bench 规则执行、PPT/视频生成、自适应日志解析、生产日志诊断、动态表单、ERP SQL、界面定制、造 Agent 的 Agent)与 10 道思考题。

## 一致与相互印证

1. **"constraints over guidance" 与公理 3 完全同构**。该章反复强调:能编码强制的规则不要写成建议;信任边界要下沉到模型无法绕过的层(数据层权限对象、服务端 ground-truth 校验);critique 操作必须由上下文之外的机制审查。这正是 Agent OS"一切特权操作可拦截、内核在分发前后发信号、SYNC sidecar 有否决权"(§1、§5.1、§8.1)的立论基础。τ-bench 例中"绝不信任模型自报参数"与我们"权限在 manifest 声明、内核运行期逐次检查,而非靠提示词约束"(§2.1、§8.2)互为印证。
2. **失败分类学四层与我们子系统划分一一对应**——API 层归 Providers(§4)、工具层归 Tool Registry(§8)、上下文层归 Compression(§7)、控制流层归 Sidecars + 预算(§5、§2.4)。这说明六子系统的职责切分覆盖了生产级 Harness 的失败域,没有整层遗漏。`ProviderError.retryable`(§4.1)与"先问重试有没有用"的分类思想一致。
3. **tool_call/tool_result 配对原子性**。该章把"配对阵损坏"列为上下文层失败,并给出"注入前修复配对"的工程实践;我们把同一要求上升为压缩子系统的可测硬约束(§7.3 不变量 2),且由 RollingWindowCompressor 的原子组结构保证而非事后检查(§7.5)。该章"朴素压缩器最常犯的错,各家 API 直接 400"的论断直接支持这一设计优先级。
4. **工具错误作为观察回写、不终止会话**(该章"turn the error into the model's input")与 §3.2 工具失败语义逐字对齐;连"附输入契约提示的结构化错误"都与 §8.1"JSON Schema 校验不合法 → 错误观察"同构。
5. **循环检测机制雷同**。该章"重复调用指纹 = hash(tool name + arguments)"与 LoopDetector 的"滑窗 name+args 哈希签名"(§5.5)是同一种实现;"先纠偏(注入消息)再强停"的两级处置也一致(§5.4)。
6. **Proposer-Reviewer 的上下文隔离收益 = SkillFrame 弹栈折叠**。该章论证双代理优于单代理自审的核心理由是上下文管理(Reviewer 不背历史版本,Proposer 只收结构化反馈)。这正是我们 §2.3"子帧中间上下文不进入父帧,弹栈时整段 transcript 折叠为一个返回值"与 §7.2 `collapse_child` 的论据——章中的应用层证据反向验证了帧隔离语义的实用价值。
7. **Artifact 模式印证 spill 策略方向**。该章"数据从数据库直达界面、LLM 不转抄"与我们"大工具输出 spill 到 blob store、上下文只留 `{ref, preview}`、模型按 ref 取回片段"(§7.2、§8.1)是同一原则在两个层面的体现:都不让大体量数据穿过 LLM 上下文。
8. **沙箱默认断网 + 限额 + 结构化超限错误**。该章"超时与超限应返回结构化错误而非静默杀死,给 Agent 下轮修正策略的机会"正是 §9.5"超限 → `LIMIT_EXCEEDED` 作为帧错误上抛、父帧 LLM 可补救"的语义;默认断网、rlimits、只读临时目录逐项对应 §9.2。
9. **持久化"可审计的状态描述"而非不透明进程**。该章对 sessionless/沙箱的调和方案与我们检查点设计(append-only 事件日志 + 版本头、快照可重建可丢弃,§13 风险表)同构。
10. **审批闸的位置**。该章工作流在"设计文档"处设人工审批;我们的 HumanApproval 挂在 `pre:tool.call` EXEC 级(§5.4)——机制相同,挂载点不同(见下节)。

## 差距与可借鉴点

按"该章有而我们缺失或更浅"排序,均说明价值:

1. **恢复环路语义与死亡螺旋防御(最重要)**。该章把错误处理单位定义为"整个恢复环路"并要求:每条恢复路径独立连败计数 + 熔断上限(阈值来自生产数据,如压缩连败 3 次即放弃);错误路径上禁用一切调 LLM 的副作用 + 递归深度计数器防级联。我们有三处恢复路径会调 LLM——压缩器的 `summarize` 策略(§7.2,经 ProviderManager)、`InjectMessage` 后的继续推理、以及父帧对子帧失败的 LLM 补救(§3.2)——任何一处自身失败都可能级联(压缩失败 → 重试压缩 → 再失败,正是该章 250k 次/天浪费的同款事故)。DESIGN.md 只在风险表提了"输出不合 schema 最多 N 次修复循环",无通用熔断与级联防御。
2. **ToolGuard 的正则路线被该章明确判死刑**。该章用 `$(echo rm) -rf /`、`find -exec rm`、`curl -o /etc/crontab` 证明关键字/正则黑名单对 Shell 组合爆炸无效,生产级 harness 用语义解析(识别每条命令的参数类型、哪些 flag 吞后续参数、嵌套危险操作)。我们 §5.5 的 ToolGuard baseline 恰是"工具名/参数正则"——作为演示样本可接受,但设计文档未指出其能力上限与升级路径。
3. **idle watchdog**。该章指出流式连接最危险的失败是静默停滞(连接活着但没有数据流),SDK 超时通常只覆盖建连不覆盖传输,需独立的空闲看门狗。我们 §4.2 只写"超时",stream 路径(§4.1 `stream()`)无停滞检测。
4. **故障边界控制与并发声明**。该章给出两条具体规则:工具须声明是否支持并发执行(默认否,fail-safe);同批次内级联中止只波及有依赖的调用,不取消独立调用、不上溯父操作。我们 §3.4 只有"每分支独立帧、独立预算记账",`parallel_invoke` 批内一个分支失败如何影响兄弟分支未定义;ToolSpec(§2.2)有 `idempotent` 但无并发安全标志。
5. **降级续跑(degrade and continue)的具体手法**。输出截断时"提高输出上限静默重发 → 追加元指令从断点续写";fallback 换模型时"先剥离前一家的专有格式块"。我们 §4.2 有 fallback 链(M5)但无跨 provider 的消息归一化要求——`ChatResponse.raw` 之外的专有格式残留会让备选模型解析失败。
6. **fs_edit 工具与文件编辑五方案**。七件套里我们独缺 Edit。该章给出明确的选型建议:自建首选 old string→new string(可预测、失败无歧义),大块编辑用首尾字符串匹配;行号方案无 IDE 深度集成会被行号漂移拖死。配套的 fs_read 应支持行区间读取并附行号前缀(模型可精确引用"src/main.py:42",降低编辑歧义)。
7. **spill preview 的头尾保留策略**。该章:长输出保留头部(错误上下文)与尾部(错误摘要),中间折叠并注明完整内容已持久化。我们 §8.1 只写"大小封顶 → 超限 spill,返回 {ref, preview}",preview 取法未定——朴素取头 N 字符会丢掉日志尾部的关键错误摘要。
8. **持久终端会话**。Coding 场景下 cd/venv/环境变量跨命令生效是刚需,该章建议默认共享长活终端。我们 `shell_exec` 的会话语义未定义;ToolContext"不碰全局状态"(§2.2)若理解为每次调用全新 shell,则 Coding 技能体验受损。可借鉴的调和:会话作为 run 作用域的显式资源句柄注入 ToolContext,而非全局状态。
9. **环境 status bar 与即时语法反馈**。前者把 cwd/git 分支/未暂存改动作为动态后缀注入(不进系统提示,保 KV Cache);后者在文件写入后自动跑 linter 并把结果并入工具返回值——"错误在引入时刻即被发现"。两者都是低成本高回报:在我们体系里,status bar 可挂在 `build_request`(§3.1),语法反馈可挂在结果归一化阶段(§8.1)或由 SYNC sidecar 用 `Modify` verdict 追加。
10. **流式执行优化**。第一个工具调用参数生成完即开始执行,与后续调用的生成重叠,显著降端到端延迟。我们 runner(§3.1)是整响应收完再批量分发,`Provider.stream`(§4.1)已预留但 runner 未消费。属优化项,不影响契约。
11. **"先分类再计数"对 ToolGuard/权限失败的启示**。该章强调 non-retryable 错误(参数非法、权限不足、工具不存在)重试无用,须改变输入或策略。我们的错误观察(§3.2)未区分 retryable 语义,LLM 可能拿不可重试错误空转——可在错误观察结构中加 `retryable` 提示,供 LoopDetector 更早介入。
12. **持久记忆的信任审查**。该章把 Persistent Memory 列为攻击放大器,要求写入长期记忆的内容过与外部输入同级的信任审查。我们长期记忆是非目标(§14),但黑板服务已预留(§11.3),开放问题 4 已在问权限统一问题——该章给出了答案的方向:写路径必须过审查,不能只是"读写走信号可审计"(§2.3)。

## 冲突或不同取舍

1. **持久会话 vs 一次性环境 / 无状态工具**。该章明确主张默认持久终端(贴合人类开发者习惯),也承认与隔离原则存在张力,其调和是"会话不得活得比沙箱久"。我们 §2.2 强调工具不碰全局状态以换可测试性。两案可调和:会话状态作为 run 作用域资源由内核持有、经 ToolContext 注入——既非工具私有全局态,也非每次全新。若坚持现状,Coding 类技能每次 shell 调用都要重做环境准备,实际不可用。
2. **审批闸挂点:工作流层 vs 工具层**。该章把人工审批放在"设计文档完成"这一工作流节点(审一份简明设计远易于审数百行代码);我们 HumanApproval 挂在 EXEC 级工具调用(§5.4)。前者拦在"动手之前",成本是打断流程;后者拦在"危险动作之前",颗粒更细但审批者看到的是命令而非意图。两案不互斥:我们的机制足以支撑前者(HumanApproval 也可订阅 `pre:skill.invoke` 或在技能内编排),但文档未提"计划审批"这一更便宜的拦截点。
3. **错误可见性哲学:暂扣 vs 全量透明**。该章主张恢复未确认失败前中间错误对用户和事件订阅者一律暂扣("恢复成功则无人察觉");我们的信号总线把所有事件广播给订阅者,TraceRecorder 全量落盘(§5.1)。对内嵌库而言我们的做法更利于调试与审计,该章的做法是面向终端用户的体验层策略——可由宿主在信号订阅侧做过滤实现,内核不必改。成立条件:产品有终端用户实时事件流时,该章方案更优。
4. **并行默认面**。该章要求工具默认声明不支持并发(fail-safe),并行是显式能力;我们默认串行(§3.4)精神一致,但一旦提供 `parallel_invoke` 而未配并发声明,等于默认所有工具可并发——比该章更激进。补上声明即可对齐。
5. **进程内压缩用 LLM 摘要 vs 该章的熔断数据**。我们 `summarize` 策略(§7.2)依赖 ProviderManager 调廉价模型,本身是一条会失败的 LLM 路径,而该章用 3000+ 连败的真实事故说明压缩路径必须熔断。不是方向冲突,是我们低估了该路径的熔断优先级(§13 风险表只提了"输出不合 schema N 次循环")。
6. **文件系统作为记忆中枢(Markdown 优先)vs 我们的非目标**。该章力主 `MEMORY.md` 式文件记忆优于向量库;我们把长期记忆服务列为非目标(§14)。对内核定位而言我们的取舍成立(记忆是宿主/技能层职责),但需注意:该章的论据(可人读人改、Git 可回滚、保序)说明"技能 + fs 工具"已能在应用层长出记忆,内核无需内建——两案实际兼容,我们的 blob store + 工作目录已是足够底座。

## 行动建议

按优先级排列,每项标注影响的子系统与设计文档小节。

**P0(影响可靠性根基,建议进 v0.4 设计稿)**

1. **引入"恢复环路"错误语义与通用熔断器**:为每条会调 LLM 的恢复/后台路径(summarize 压缩、输出修复循环、fallback)配独立连败计数器与熔断上限;错误路径上默认禁用调模型的副作用;提供递归深度计数。落到 §3.2(错误处理)与 §7.2(summarize 失败策略),风险表(§13)补"死亡螺旋"一行。受影响:Kernel Runner、Context Compression、Providers。
2. **ToolGuard 能力上限声明 + 语义解析升级路径**:在 §5.5 明确"正则规则表仅覆盖显见模式,对 shell 组合爆炸无效"，`shell_exec` 的防护主体应是沙箱(§9.2)+ 权限等级(§8.2)而非 ToolGuard;语义解析器(命令 AST/参数规则库)作为 ToolGuard 的后续替换实现预留。受影响:Sidecars §5.4/§5.5。
3. **ProviderManager 流式停滞 idle watchdog**:stream 路径加"N 秒无新 chunk 判定停滞 → 杀流重试"的看门狗,与建连超时并列。落到 §4.2 弹性条款。受影响:Providers §4。

**P1(具体、低成本、直接提升 Coding 场景可用性)**

4. **新增 `fs_edit` 内置工具**:old_string→new_string 语义(须唯一匹配,否则报错),大编辑可后续加首尾匹配变体;`fs_read` 增加行区间参数与行号前缀输出。落到 §8.3/§8.4 内置工具清单。受影响:Tool Registry。
5. **spill preview 改头尾保留**:§8.1 结果归一化与 §7.2 spill 策略明确 preview = 头部 + 尾部 + 中间折叠标注(附总字节数与 ref)。受影响:Tool Registry、Context Compression。
6. **定义 parallel_invoke 批内故障语义 + ToolSpec 增并发标志**:批内某分支失败只级联中止声明了依赖关系的同批分支,不影响独立分支与父帧;ToolSpec(§2.2)加 `concurrency_safe: bool = False`。落到 §3.4。受影响:Kernel Runner、契约层 api/v1。
7. **错误观察结构加 `retryable` 字段**:对齐 ProviderError 的分类思想,工具/schema 校验/权限拒绝标 `retryable: false`,供模型与 LoopDetector 区分"该换策略"与"该重试"。落到 §3.2、§8.1。受影响:Tool Registry、契约层。

**P2(值得做,可随 M5 或之后)**

8. **run 作用域持久终端会话**:内核持有每 run 一个默认 shell 会话句柄(工作目录/环境变量/后台任务),经 ToolContext 注入 `shell_exec`;会话生命周期 ≤ 沙箱生命周期,销毁前把可序列化状态写入工作区(对齐该章 sessionless 两层方案,也服务 M5 检查点恢复)。落到 §2.2、§8.4、§13 M5。受影响:Tool Registry、Kernel。

该章后半(元能力六方向:思维工具、规则代码化、多媒体、适配器、Generative UI、Bootstrapping)与内核设计**关联度中等偏低**——它们是应用层模式,不改变任何契约。但其中三点仍具结构价值:τ-bench 三层防护为"内核强制 vs 提示词建议"提供了实验级证据(§8.2 的立论);Proposer-Reviewer 为帧隔离语义提供了应用层验证(§2.3);Artifact 模式为 spill/blob 设计提供了方向确认(§7.2)。Bootstrapping、Generative UI、多媒体生成三节对内核无直接影响,本报告不强行映射。
