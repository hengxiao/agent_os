# 文档行内批注气泡竞品分析报告

> 调研目标：对比市面上成熟的行内批注/评论系统，为 Agent OS 文档编辑器的批注气泡 UX 优化提供设计参考。
> 
> 我们的设计现状（基于 2026-08-12.4 构建验收）：行文级批注（气泡），右键开泡，选区高亮关联，气泡吸附文档右侧边缘，标记缩成 💬 小圆标，消息流对话形式，支持"采纳成批注"，源码/预览双视图，moe 主题。

## 1. Google Docs Comments

### 1.1 概述

Google Docs 的评论系统（Comments）是**文档协作批注的行业标杆**，自 2008 年推出以来持续迭代，目前全球月活用户超过 10 亿。其核心定位是"多人异步审阅文档"，设计理念围绕**最小干扰 + 最大上下文保留**展开。

**核心交互流程：**
1. **触发方式**：选中文字 → 点击工具栏评论按钮（💬）或 `Ctrl+Alt+M` 快捷键
2. **气泡定位**：在选区右侧边缘弹出一个小型输入框，提交后缩成右侧边栏中的评论卡片
3. **锚定机制**：选区文字自动添加黄色高亮底，评论卡片左侧显示对应的高亮条，形成视觉连线
4. **消息流**：评论卡片内支持多轮回复（thread），每条评论可 `@mention`、添加 emoji reaction
5. **Resolve 机制**：评论可标记为"已解决"（Resolve），解决后高亮消失，评论卡片收起为"已解决"列表
6. **Suggestion 模式**：在评论基础上支持"建议修改"（Suggesting），直接提出替换文本，作者可一键采纳

### 1.2 与我们的设计异同

| 维度 | Google Docs | 我们的设计 |
|------|------------|-----------|
| **触发方式** | 工具栏按钮 / 快捷键 | **右键菜单**（更直觉） |
| **气泡初始位置** | 选区右侧紧邻浮出 | 文档**右侧边缘固定面板** |
| **高亮样式** | 黄色底（`#fce8b2`），醒目但柔和 | 半透明红底（`srgb 0.76 0.14 0.36 / 0.15`），在 moe 主题下呈浅粉 |
| **消息流容器** | 右侧固定边栏，评论按文档位置排序 | 浮动气泡，每个批注独立气泡 |
| **多轮对话** | 同一 thread 内紧凑排列 | 同一气泡内消息流 |
| **Resolve 状态** | ✅ 有明确"已解决"状态和归档 | ❌ 无（仅有删除） |
| **Suggestion 修改** | ✅ 支持提出替换文本，一键采纳 | ✅ 支持"采纳成批注"（但机制不同） |
| **AI 参与** | ❌ 无原生 AI 回复 | ✅ 核心差异化：AI Agent 可直接在批注内对话 |
| **批量审阅** | ✅ 支持批量查看、搜索、筛选评论 | ❌ 无 |
| **通知体系** | ✅ 邮件通知 + 应用内通知 + 摘要邮件 | ❌ 无 |

### 1.3 优缺点分析

**Google Docs 的优点：**

1. **Resolve 状态机是最精髓的设计**：评论不是"非生即死"，而是有完整的生命周期（打开 → 讨论中 → 已解决 → 可重新打开）。这避免了"删除批注 = 丢失讨论历史"的问题，也让文档审阅流程有明确的进度感。
2. **右侧边栏模式在信息密度上胜出**：当文档有 20+ 条评论时，Google Docs 的边栏可以紧凑列出所有评论，而我们的独立气泡会互相遮挡或堆叠。
3. **Suggestion 模式实现了"评论即修改"**：审阅者不只是说"这里不对"，而是直接给出修改建议，作者一键采纳即可，极大减少了来回沟通成本。
4. **高亮-评论的视觉连线清晰**：黄色高亮条与右侧评论卡片的颜色对应，即使滚动文档也能快速定位。

**Google Docs 的局限：**

1. **无原生 AI 对话能力**：评论是纯人类之间的讨论，无法像我们的设计那样让 AI Agent 直接在批注内回复、解释、执行修改。
2. **对实时协作的依赖**：评论系统假设文档处于实时多人编辑状态，对于单人+AI 的工作流（我们的核心场景）不是最优。
3. **移动端体验差**：在手机上，右侧边栏被迫变成底部抽屉，评论与高亮的对应关系断裂。

**我们的优点（相对 Google Docs）：**

1. **AI 原生设计**：批注气泡内直接接入 LLM 对话，这是 Google Docs 完全不具备的能力。
2. **右键触发更直觉**：Google Docs 需要先选中文字再找工具栏按钮，我们的右键菜单一步直达。
3. **气泡不占用固定边栏空间**：Google Docs 的右侧边栏会挤压文档可视区域，我们的气泡叠加在文档上方，不侵占编辑空间。

**我们的缺点（相对 Google Docs）：**

1. **缺少 Resolve 状态**：当前只有"删除"，没有"已解决但保留历史"的状态，导致讨论进度不可追踪。
2. **气泡在评论多时互相遮挡**：验收测试中发现同一行多个气泡会重叠、y 坐标异常。
3. **无批量审阅视图**：无法像 Google Docs 那样一览所有未解决评论。

### 1.4 如果要学习，怎么做

| 学习项 | 具体做法 | 优先级 |
|--------|---------|--------|
| **引入 Resolve 状态机** | 在气泡头部增加"✓ 已解决"按钮；解决后高亮变淡/消失，标记变成灰色；已解决评论可折叠到"已解决"列表 | **P0** |
| **右侧边栏总览模式** | 当批注数量 > 5 时，提供"切换到边栏视图"选项，类似 Google Docs 的右侧评论列表，按文档位置排序 | P1 |
| **Suggestion 模式增强** | 允许 AI 在回复中提出具体的文本替换建议（diff 形式），用户可一键"采纳修改"而非仅"采纳成批注" | P1 |
| **高亮-评论视觉连线** | 在高亮文字和气泡之间画一条细线（类似 Google Docs 的黄色连线），尤其在气泡收起为 💬 标记时有用 | P2 |

## 2. Figma Comments

### 2.1 概述

Figma 的评论系统（Comments）是**设计工具领域的标杆**，其核心定位是"在视觉画布上留下精准反馈"。与文档类批注不同，Figma 的评论锚定在**像素坐标**而非文本选区，这让它成为三个竞品中与我们的设计**差异最大**的一个。

**核心交互流程：**
1. **触发方式**：按 `C` 进入评论模式 → 点击画布任意位置（精确到像素）→ 弹出评论输入框
2. **气泡定位**：评论输入框出现在点击位置附近（可拖拽调整），提交后缩成一个"图钉"（Pin）标记
3. **锚定机制**：Pin 标记精确位于点击的像素坐标，即使被评论的图层移动，Pin 也会跟随移动（Layer-attached）或保持原位（Canvas-attached）
4. **消息流**：点击 Pin 后弹出评论卡片，支持多轮回复、@mention、emoji reaction
5. **视觉密度管理**：多个 Pin 靠近时会自动聚合成"簇"（Cluster），显示数字徽章，点击后展开为列表
6. **状态管理**：评论可标记为"已解决"（Resolved），解决后 Pin 变为半透明/消失
7. **AI 增强（2025+）**：Figma 引入了 AI Design Agent，可对设计进行自动评审，并在评论区生成反馈摘要

### 2.2 与我们的设计异同

| 维度 | Figma Comments | 我们的设计 |
|------|---------------|-----------|
| **锚定对象** | **像素坐标 / 图层** | **文本选区 / 行号+列号** |
| **触发方式** | `C` 键 + 点击画布 | 右键菜单 |
| **气泡初始位置** | 点击位置附近，**可自由拖拽** | 文档右侧边缘固定位置 |
| **标记形态** | 彩色头像 Pin（含用户头像） | 💬 小圆标（无头像） |
| **多评论聚合** | ✅ 自动聚合成簇（Cluster） | ❌ 无 |
| **图层跟随** | ✅ 评论可附着于图层，图层移动时 Pin 跟随 | ❌ 无（文本是流动的） |
| **Resolve 状态** | ✅ 有"已解决"，解决后 Pin 变灰/消失 | ❌ 无 |
| **移动端适配** | Figma Mobile 有专门的评论视图 | 未测试 |
| **AI 参与** | ✅ AI Design Agent 可生成评审摘要 | ✅ LLM Agent 直接在气泡内对话 |
| **视觉干扰** | Pin 默认可见，画布密集时会显得杂乱 | 标记较小，收起后干扰低 |

### 2.3 优缺点分析

**Figma 的优点：**

1. **像素级精准锚定是杀手级体验**：设计稿上的反馈必须精确到"这个按钮的右上角阴影不对"，Figma 的 Pin 式锚定做到了这一点。文档类批注虽然不需要像素级，但"精准到字符"的锚定逻辑值得借鉴。
2. **Pin 可拖拽调整位置**：用户发完评论后如果觉得 Pin 遮挡了设计元素，可以直接拖拽 Pin 到空白处，而不影响锚定的实际目标。这种"视觉锚点与逻辑锚点分离"的设计非常聪明。
3. **自动聚合（Cluster）解决密度问题**：当多个评论聚集在一起时，Figma 不会让它们堆叠成乱麻，而是聚合成带数字的簇，点击后展开列表。这是处理高密度批注的典范。
4. **评论与图层的生命周期绑定**：如果设计师移动了一个组件，附着在其上的评论 Pin 会自动跟随，避免了"评论悬空"的问题。

**Figma 的局限：**

1. **不适用于文本流**：Figma 的 Pin 锚定像素坐标，当文本内容变化（增删改）时，Pin 不会自动跟随文本移动，容易"悬空"。我们的设计锚定行号+列号，文本变化时可以通过 diff 算法重新定位。
2. **画布模式与阅读模式冲突**：Figma 的评论 Pin 在演示模式（Presentation）下会干扰观看体验，需要额外隐藏。我们的 💬 标记在阅读模式下相对低调。
3. **缺少文本选区关联**：Figma 的评论是纯位置锚定，没有"这段文字被高亮"的视觉反馈，反馈的精确性依赖发评论者的文字描述。

**我们的优点（相对 Figma）：**

1. **文本选区高亮提供更精确的上下文**：Figma 的评论靠文字描述定位，我们的设计直接高亮被评论的文本，读者无需猜测"他说的是哪段"。
2. **右键触发更符合文本编辑习惯**：Figma 的 `C` 键+点击是设计工具范式，对文档编辑用户来说不够直觉。
3. **气泡内直接 AI 对话**：Figma 的 AI 评审是生成摘要，而我们的 AI 可以在批注内进行多轮对话并直接执行修改。

**我们的缺点（相对 Figma）：**

1. **气泡位置不可调整**：验收测试中发现我们的气泡始终吸附在右侧边缘，用户无法像 Figma 那样拖拽气泡到不遮挡内容的位置。
2. **无聚合机制**：当同一区域有多条批注时（如 E3 测试），气泡互相遮挡，没有 Figma 的 Cluster 机制。
3. **标记无头像/用户信息**：Figma 的 Pin 带用户头像，一眼就能看出谁留的批注，我们的 💬 标记是统一图标。

### 2.4 如果要学习，怎么做

| 学习项 | 具体做法 | 优先级 |
|--------|---------|--------|
| **气泡可拖拽调整位置** | 允许用户拖拽气泡到任意位置，气泡通过一条细线与锚点（高亮文字/💬 标记）连接，类似 Figma 的 Pin 与评论框的关系 | **P0** |
| **引入 Cluster 聚合机制** | 当同一行/段有多个 💬 标记时，自动聚合成带数字的簇，点击后展开为列表或轮播浏览 | P1 |
| **标记增加用户头像/颜色** | 在 💬 标记上叠加用户头像或分配固定颜色，让多人协作时一眼识别批注归属 | P1 |
| **视觉锚点与逻辑锚点分离** | 逻辑锚点始终是文本选区（行号+列号），但视觉锚点（气泡位置）可由用户调整；当文本变化时，气泡自动重新吸附到新的文本位置 | P2 |

## 3. GitHub PR Review（行级评论）

### 3.1 概述

GitHub Pull Request 的行级评论（Line Comments / Review Comments）是**代码审阅领域的事实标准**，全球数千万开发者日常使用。其核心定位是"在代码 diff 上留下精准的审阅意见"。虽然场景是代码而非文档，但其**行级锚定、diff 上下文、建议修改（Suggested Changes）**等机制对文档批注系统有极高的参考价值。

**核心交互流程：**
1. **触发方式**：在 PR 的 "Files changed" 标签页，hover 到代码行号旁出现蓝色 💬 图标，点击后弹出评论输入框
2. **气泡定位**：评论输入框附着在具体代码行下方，展开时推开后方的 diff 内容
3. **锚定机制**：精确锚定到**文件 + 行号范围**（可单选一行或 Shift 多选连续行），GitHub 通过 Git blob hash 确保即使代码被修改，评论也能通过 diff 算法重新定位（或标记为 outdated）
4. **消息流**：支持多轮回复（thread），每条评论可引用代码片段（`> ` 语法高亮）
5. **Suggested Changes**：审阅者可以直接在评论中提出代码修改建议（```suggestion 代码块），作者可一键"Commit suggestion"将修改直接提交到 PR
6. **Outdated 标记**：当被评论的代码在后续提交中被修改，评论自动标记为 "Outdated"（灰色收起状态），但仍可查看
7. **Review 状态**：评论可被标记为"Resolved"，PR 可设置"要求所有评论解决后才允许合并"

### 3.2 与我们的设计异同

| 维度 | GitHub PR Review | 我们的设计 |
|------|-----------------|-----------|
| **锚定对象** | **代码行号 + 文件路径 + Git commit hash** | **文档行号 + 列号** |
| **上下文保留** | ✅ 自动保留被评论代码的原始快照 | ⚠️ 仅保留 quote 文本，无快照 |
| **触发方式** | Hover 行号 → 点击 💬 图标 | 右键菜单 |
| **气泡位置** | 代码行下方，推开后方内容 | 文档右侧边缘 |
| **Suggested Changes** | ✅ 可直接提出代码修改，一键提交 | ✅ "采纳成批注"（但需 AI 执行） |
| **Outdated 状态** | ✅ 代码变动后自动标记为过时 | ❌ 无（文本修改后批注可能悬空） |
| **Diff 视图** | ✅ 天然在 diff 上下文中审阅 | ✅ 支持源码/预览切换 |
| **多轮审阅** | ✅ 支持多次 Review，每次可要求修改 | ❌ 无 |
| **AI 参与** | ✅ Copilot 可生成 Review 摘要 | ✅ LLM Agent 在气泡内对话 |
| **协作模式** | 异步 + 同步混合（通知体系完善） | 主要是同步对话 |

### 3.3 优缺点分析

**GitHub PR Review 的优点：**

1. **Outdated 机制是代码审阅的精髓**：当代码被修改后，原有评论不会凭空消失或错位，而是被标记为"已过时"，仍可查看上下文。这是处理"被评论内容发生变化"这一复杂问题的最佳实践。
2. **Suggested Changes 实现了"评论即提交"**：审阅者不只是提意见，而是直接给出修改代码，作者点一下按钮就生效。这比我们的"采纳成批注"更进一步——不需要再让 AI 去理解和执行。
3. **Diff 上下文让审阅有全局视角**：GitHub 的审阅始终在看"改了什么"，而不是"改完后是什么样"。文档批注也应该考虑在"修订模式"下审阅，而不仅是"最终视图"。
4. **Review 状态与合并门禁绑定**：评论是否全部解决，直接决定 PR 能否合并，这让审阅流程有强制力。我们的文档审阅缺少这种"完成度追踪"。

**GitHub PR Review 的局限：**

1. **仅适用于代码，不适用于富文本文档**：GitHub 的行级评论基于纯文本 diff，对格式化文档（Markdown 渲染后的视图）无能为力。我们的设计天然支持富文本。
2. **交互门槛高**：需要理解 PR、commit、diff 等概念，非技术用户难以使用。我们的设计面向更广泛的用户群体。
3. **缺少实时对话感**：GitHub 的评论是异步的，回复可能要等几小时甚至几天。我们的气泡内 AI 对话是实时的。

**我们的优点（相对 GitHub）：**

1. **面向富文本文档而非代码**：支持 Markdown 渲染、预览视图，这是 GitHub 行级评论做不到的。
2. **AI 实时对话**：GitHub 的审阅是异步人类之间的讨论，我们的设计让 AI 可以实时参与并执行修改。
3. **更低的认知门槛**：右键 → 批注 → 对话，三步完成，不需要理解 Git 或 PR 的概念。

**我们的缺点（相对 GitHub）：**

1. **缺少 Outdated 机制**：当用户修改了被批注的文本后，原有批注没有"已过时"状态，可能导致批注悬空或错位。
2. **无代码快照**：GitHub 保留被评论代码的原始快照，我们仅保留 quote 文本，如果文本被大幅修改，quote 的上下文可能丢失。
3. **无审阅完成度追踪**：GitHub 可以统计"还有多少未解决评论"，我们的设计缺少这种全局进度指示。

### 3.4 如果要学习，怎么做

| 学习项 | 具体做法 | 优先级 |
|--------|---------|--------|
| **引入 Outdated 状态** | 当被批注的文本被修改后，自动检测批注锚点是否仍有效；若文本变化导致锚点丢失，将批注标记为"已过时"（灰色），但仍可查看 quote 和原始上下文 | **P0** |
| **保留文本快照** | 创建批注时，不仅记录 quote 文本，还记录该批注创建时整段/整行的完整文本快照；当文本变化后，用户可在批注内查看"原文快照" | P1 |
| **Suggested Changes 直接修改** | 允许 AI 在回复中直接输出文本替换建议（diff 形式），用户可一键"采纳修改"直接替换文档文本，无需再走一遍 AI 对话 | P1 |
| **审阅进度指示器** | 在文档工具栏增加"未解决批注数"徽章，类似 GitHub PR 的"X unresolved conversations" | P2 |
| **批量 Resolve** | 支持一键"全部标记为已解决"，或批量选择多个批注统一操作 | P2 |

## 5. 学习路径与优先级建议

### 5.1 立即做（P0 — 影响验收通过）

基于验收测试中发现的偏离项，以下改进可直接借鉴三个竞品的成熟机制：

| 问题 | 借鉴来源 | 具体方案 |
|------|---------|---------|
| **E6: 气泡高度无上限** | Google Docs 边栏 + Figma 可拖拽 | 引入气泡高度上限（max-height: 320px），消息流内部滚动；同时允许用户拖拽气泡位置 |
| **E7: 连发吞消息** | GitHub 评论提交防抖 | 前端发送按钮增加防抖（300ms 内合并多次点击为一次），或发送后锁定按钮直到后端确认 |
| **气泡互相遮挡** | Figma Cluster 聚合 | 同一区域多个标记时自动聚合为数字簇，点击后展开 |
| **缺少 Resolve 状态** | Google Docs + GitHub | 引入"已解决"状态，解决后高亮变淡、标记变灰，评论可折叠到"已解决"列表 |

### 5.2 短期做（P1 — 显著提升体验）

| 改进项 | 借鉴来源 | 预期收益 |
|--------|---------|---------|
| **Outdated 状态** | GitHub | 文本被修改后批注不会悬空，用户始终知道哪些批注仍有效 |
| **文本快照保留** | GitHub | 即使原文被大幅修改，用户仍可查看批注创建时的上下文 |
| **气泡可拖拽** | Figma | 用户可调整气泡位置避免遮挡内容 |
| **右侧边栏总览视图** | Google Docs | 批注多时可切换为列表视图，一览全局 |
| **标记增加头像/颜色** | Figma | 多人协作时快速识别批注归属 |
| **一键采纳修改（diff 形式）** | GitHub Suggested Changes + Google Docs Suggestion | AI 提出具体文本替换，用户一键采纳，减少对话轮次 |

### 5.3 中长期做（P2 — 建立差异化优势）

| 改进项 | 设计思路 | 预期收益 |
|--------|---------|---------|
| **批注生命周期仪表盘** | 融合 Google Docs Resolve + GitHub Review 状态 | 在文档顶部显示"审阅进度：3 未解决 / 12 已解决 / 2 已过时"，让文档审阅有明确的"完成度" |
| **AI 主动批注建议** | 借鉴 Figma AI Design Agent | AI 在阅读文档时主动发现潜在问题（如"这段和上面重复了"），并自动创建批注供用户确认 |
| **批注搜索与筛选** | Google Docs | 支持按作者、状态、关键词搜索批注 |
| **邮件/通知摘要** | Google Docs + GitHub | 每日/每周发送批注活动摘要，避免用户错过重要反馈 |
| **批注导出为任务** | GitHub PR 与 Issue 关联 | 将批注一键转为看板任务或 GitHub Issue，打通工作流 |

### 5.4 我们应该坚持的核心差异化

在借鉴竞品的同时，以下是我们的**护城河**，不应被竞品范式稀释：

1. **AI 实时对话是核心体验**：Google Docs、Figma、GitHub 都是人类之间的异步讨论，我们的设计让 AI 直接参与批注对话并执行修改，这是独一无二的优势。任何借鉴都不应牺牲这个核心体验。
2. **右键触发的一步直达**：三个竞品都需要多步操作（选文字 → 找按钮 / 按快捷键 / hover 等），我们的右键菜单是更直觉的触发方式。
3. **文档编辑与批注的无缝融合**：我们的批注气泡直接悬浮在编辑器上，用户可以在批注对话和文档编辑之间快速切换，不像 GitHub 那样需要切换标签页。

---

> **报告总结**：三个竞品中，**Google Docs** 最值得学习的是 Resolve 状态机和右侧边栏总览；**Figma** 最值得学习的是 Pin 可拖拽和 Cluster 聚合机制；**GitHub PR** 最值得学习的是 Outdated 状态和建议修改直接提交机制。建议优先实施 P0 项（气泡封顶内滚、防抖防吞、Resolve 状态），这些改进可以直接解决当前验收测试中的偏离项。
