## 1. 三个方案的交互模型

### 方案 A · 三栏批注驱动(spec 原版)

```
既有 v003(结构化只读) │ 批注列表 + 补充 → ✨生成 │ 候选 v004(diff摘要+双侧分数)
```

- 既有版本的每个字段/段落/用例都有 💬 锚点,批注先汇聚成"一轮";
- 一轮批注 → 一次显式生成 → 右侧候选 + 双侧测试分数表;
- 接受/重生成是这轮循环的出口,版本下拉 + rewind 在顶栏。

### 方案 B · 对话驱动(chat-native)

```
上:既有 ⇆ 候选(紧凑并排)
下:对话流(批注=用户气泡)→ 输入框
```

- 没有独立批注面板:批注就是聊天消息,随手说一句就刷新候选;
- 版本是一行 chip(v1 v2 v3 v4候选),切换轻;
- 生成节奏是连续的,不是"一轮一次"的批处理。

### 方案 C · 双栏 diff + 内嵌批注

```
左:既有(边注💬钉在内容旁) │ 右:diff(prompt 红绿增删 / 字段新旧两列 / tests +新增)
```

- GitHub PR review 心智:diff 是第一公民,评审逐处进行;
- 批注以 margin note 挂在具体内容旁边,所见即所批;
- 接受/重生成在顶栏,没有中间层。

## 2. 对比表

| 维度 | A 三栏批注 | B 对话驱动 | C diff + 边注 |
|---|---|---|---|
| 信息架构 | 三栏:内容/意见/产物 | 上下:产物/对话 | 双栏:内容/diff |
| 批注形态与效率 | 锚点 + 列表,成轮提交(精确但步骤多) | 气泡,随手说(快但锚点弱) | 边注,所见即所批(精确且直观) |
| 评审密度(一屏信息量) | 中(三栏分摊) | 低(对话吃屏) | 高(diff 浓缩) |
| diff 可读性 | 摘要 + 分数表(概括) | 弱(埋在对话里) | 最强(行级红绿 + 新旧列) |
| 生成节奏感 | 批处理:一轮 → 一版(清晰) | 流式:随说随改(顺滑) | 随批注累积,diff 常开 |
| 学习成本 | 中(新概念"轮") | 最低(就是聊天) | 低(PR review 既视感) |
| 实现成本(对照 lab.js) | 高:批注锚定模型 + 三栏同步 | 中:复用现有 chat 栏 + 版本并排 | 中高:diff 渲染是新组件 |
| 适配人群 | 精细评审型(逐条抠) | 快改快走型(说两句就完) | 小步迭代型(边改边看) |

## 3. 各自的风险

- **A**:三栏在窄屏拥挤;批注列表与锚点的双向同步(点批注跳锚点)做不好
  会变成"两张皮";"轮"的概念需要用户适应。
- **B**:批注难以精确锚定——"改 description"和"改 prompt 第二段"在对话里
  都是一句话,生成上下文的意图还原全靠模型,细粒度评审乏力;长对话后
  哪条意见进了哪一版不可追溯。
- **C**:diff 视图实现最重(prompt 段级 diff、字段级新旧列、tests 增删三类
  渲染);边注与 diff 同屏时,宽屏利用率依赖布局功底;生成入口不如 A 显眼。

## 4. 看样板时重点对比的 5 个问题

1. 你批注时,更想**对着内容点**(A/C 的锚点/边注)还是**对着列表/对话写**(B)?
2. 你判断"这一版改得行不行"时,先看 **diff 细节**(C)还是 **分数与摘要**(A)?
3. 你的典型迭代是**一轮 3-5 条意见批量改**(A)还是**说一句改一句**(B)?
4. 版本回溯(rewind)在你的工作流里多常用?哪个方案的版本入口你最顺手?
5. 六主题下(样板顶部可切),哪个布局在你的常用主题里依然清爽?

## 5. 推荐意见

- **精细评审选 A**:锚点 + 成轮 + 双侧分数是最完整的安全感,也是 spec 默认形态;
- **快改快走选 B**:日常 80% 的迭代是"说两句",chat-native 成本最低;
- **小步迭代选 C**:当改动需要逐处确认(trust/白名单/tier 相关)时,diff
  第一公民最不容易看漏;
- **可执行的混合策略:A 为骨架 + C 的 diff 视图**——三栏的右栏候选区从
  "摘要+分数表"升级为 C 的行级 diff 视图,B 的输入框作为 A 中栏的补充
  说明框存在(现状 A 已有此物)。这样锚定、成轮、diff 三者兼得,
  且右栏 diff 组件可以复用到 C 的完整形态。
