# Agent OS 文档编辑器：批注批处理工作流设计（v2）

> 版本：2026-08-13
> 状态：设计提案
> 灵感来源：GitHub PR Review 行级评论 + Google Docs Suggestion 模式

---

## 1. 核心理念转变

### 1.1 从"对话"到"批注"

| 维度 | v1（当前） | v2（新设计） |
|------|-----------|-------------|
| **批注本质** | 微型聊天室（多轮对话） | **单向批注卡片**（一条意见 = 一条记录） |
| **AI 参与方式** | 每条批注内 AI 实时回复 | AI 只在点击"生成下一版本"时介入 |
| **工作流节奏** | 流式、实时、碎片化 | **批量、阶段化、有节奏** |
| **版本控制** | 无（直接覆盖原文） | **完整版本链**（每次生成 = 新版本） |
| **用户心智模型** | "和 AI 聊天改文档" | "先提意见，再让 AI 统一改" |

### 1.2 为什么这样更好

1. **符合人类审阅习惯**：人看文档时，是先通读、边读边标记问题，最后统一修改。v1 的"说一条改一条"打断了阅读流。
2. **AI 有全局上下文**：一次性把所有批注 + chat 上下文喂给 AI，它能做跨段落的一致性修改，而非局部补丁。
3. **可回溯、可对比**：每次生成都是完整版本，用户可以 A/B 对比两个版本，而不是在对话记录里翻找。
4. **降低前端复杂度**：气泡不需要支持消息流、滚动、连发防抖等，大幅简化。

## 2. 双轨输入系统

用户在修改文档时，通过**两个独立的输入通道**表达修改意图：

### 2.1 通道 A：Chat（全局/宏观）

**用途**：针对文章整体结构、风格、逻辑、大纲的修改意见。

**位置**：右侧面板（现有 chat 区域）。

**交互**：
- 用户在 chat 中输入：`"第二段和第三段逻辑重复，合并成一个段落，并补充竞品分析"`
- 这条消息**不会立即修改文档**，只是被记录为"待执行的宏观指令"
- 消息旁显示状态徽章：`⏳ 待生成` → `✅ 已应用（v3）`

**特点**：
- 可以多轮对话澄清需求（AI 可以追问细节）
- 对话内容作为"生成上下文"的一部分
- 支持引用文档中的具体段落（`@第7行` 或拖拽选区）

### 2.2 通道 B：Annotation（局部/微观）

**用途**：针对具体句子、词语、标点的精修意见。

**位置**：直接在文档上，右键触发。

**交互**：
1. 用户在文档某段文字上**右键** → 弹出小型输入框（单行/多行 textarea）
2. 输入批注意见：`"这里用词太口语化，改成正式书面语"`
3. 按 Enter 或点击"添加" → 气泡收起，变成一个**小标记**（💬 或带数字的徽章）
4. 被批注的文字出现**高亮底**（浅粉色，对应 moe 主题）

**特点**：
- **单条批注 = 单条记录**，不支持多轮对话
- 批注内容简洁，通常 1-2 句话
- 批注旁显示**状态**：`⏳ 待处理` / `✅ 已应用（v3）` / `❌ 已忽略`

## 3. 批注数据结构（v2）

```typescript
interface Annotation {
  id: string;                    // 唯一标识
  type: 'inline';                // 未来可扩展为 'block', 'range'
  
  // 锚定信息
  anchor: {
    version: number;             // 批注创建时的文档版本号
    path: string;                // 文件路径（如 doc.md）
    line: number;                // 行号（1-based）
    columnStart: number;         // 起始列
    columnEnd: number;           // 结束列
    quote: string;               // 被批注的原文快照（创建时的文本）
  };
  
  // 批注内容
  content: string;               // 用户输入的批注意见
  createdAt: string;             // ISO 时间戳
  createdBy: 'user' | 'ai';      // 谁创建的（支持 AI 主动批注）
  
  // 状态
  status: 'pending' | 'applied' | 'ignored' | 'outdated';
  appliedInVersion: number | null;  // 在哪一个版本中被应用/忽略
  
  // 生成追踪
  generation: {
    appliedByVersion: number;    // 在哪个版本生成中被处理
    result: 'accepted' | 'rejected' | 'partial';  // AI 如何处理这条批注
    aiNote: string | null;       // AI 对处理结果的说明（如"已根据批注意见合并了第二、三段"）
  } | null;
}
```

### 3.1 状态流转

```
⏳ pending ──[用户点击"生成下一版本"]──→ 🔄 processing ──[AI 处理完成]──→ ✅ applied
                                                              │
                                                              └──────────────────────────→ ❌ ignored
                                                              
⏳ pending ──[原文被修改导致锚点失效]──→ ⚠️ outdated
```

## 4. 版本控制系统

### 4.1 版本链（Version Chain）

每次点击"生成下一版本"，后台创建一个新的文档版本，同时保留完整的**生成上下文**。

```typescript
interface DocumentVersion {
  version: number;               // 版本号（从 v1 开始递增）
  content: string;               // 该版本的完整文档内容（Markdown）
  createdAt: string;             // 生成时间
  
  // 生成来源
  parent: number;                // 基于哪个版本生成（通常为 version - 1）
  
  // 生成输入
  generationInput: {
    chatContext: ChatMessage[];  // 生成时的 chat 上下文（最后 N 条）
    annotations: Annotation[];   // 生成时的所有 pending 批注
    userPrompt: string | null;   // 用户点击生成时附加的指令（可选）
  };
  
  // 生成结果追踪
  annotationResults: {
    annotationId: string;
    status: 'applied' | 'ignored' | 'partial';
    aiNote: string;
  }[];
  
  // 回滚标记
  rolledBackTo: number | null;   // 如果用户从该版本回滚，记录回滚目标
}
```

### 4.2 版本时间线 UI

在文档工具栏或侧边栏增加一个**版本时间线**组件：

```
版本历史                    [对比模式] [回滚到此前版本]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
● v5  当前                  2条批注待处理    [生成下一版本]
│     刚刚                  3条 chat 消息
│
○ v4  ← 基于 v3 生成        4条批注已应用    [查看差异]
│     3 小时前              2条已忽略
│
○ v3  ← 基于 v2 生成        3条批注已应用    [查看差异]
│     昨天                  
│
○ v2  ← 基于 v1 生成        2条批注已应用    [查看差异]
│     前天
│
○ v1  初始版本              0 条批注         [查看]
      创建时间
```

**交互**：
- 点击任意版本 → 预览该版本内容（只读）
- 点击"查看差异" → 显示该版本与上一版本的 diff（类似 GitHub PR 的 Files changed）
- 点击"回滚到此前版本" → 从该版本重新开始编辑（该版本成为新的"当前"，后续生成继续递增版本号）

### 4.3 Diff 视图

生成新版本后，自动切换到 **Diff 视图**，高亮显示：
- 🟢 新增内容
- 🔴 删除内容
- 🟡 修改内容（行内 diff）

每条变更旁显示：是由哪条批注 / 哪条 chat 消息触发的。

## 5. 完整交互流程

### 5.1 阶段一：阅读与批注（Annotate）

```
用户打开文档 v5
  ↓
通读文档，发现问题：
  - 第 3 行用词太口语化 → 右键 → 输入"改为正式书面语" → Enter
  - 第 7 行缺少数据来源 → 右键 → 输入"补充用户调研的具体数据" → Enter
  - 整体结构需要调整 → 右侧面板 chat 输入"把第二部分放到前面" → Send
  ↓
文档上出现 2 个 💬 标记 + 右侧面板 1 条 chat 消息
状态栏显示："2 条批注待处理 · 1 条 chat 待应用"
```

### 5.2 阶段二：审阅与调整（Review）

```
用户检查已添加的批注：
  - 点击 💬 标记 → 弹出批注卡片（可编辑、可删除）
  - 右侧面板可查看所有批注列表
  - 可继续添加更多批注或 chat 消息
  - 可删除不需要的批注
  ↓
用户确认批注和 chat 内容已完备
```

### 5.3 阶段三：生成（Generate）

```
用户点击工具栏按钮 [🔄 生成下一版本]
  ↓
前端发送请求：
  {
    currentVersion: 5,
    chatContext: [...],
    annotations: [anno_1, anno_2],
    userPrompt: "（可选）这次生成请特别注意保持技术文档的严谨性"
  }
  ↓
后端 AI 处理：
  1. 读取 v5 完整文档内容
  2. 读取所有 pending 批注 + chat 上下文
  3. 生成修改后的 v6 内容
  4. 记录每条批注的处理结果（应用/忽略/部分应用）
  5. 保存 v6 到版本链
  ↓
前端切换到 Diff 视图（v5 → v6）
  - 高亮所有变更
  - 每条变更旁标注来源批注
  - 批注标记状态更新：⏳ → ✅/❌
```

### 5.4 阶段四：验证与迭代（Iterate）

```
用户查看 Diff：
  - 满意 → 点击 [✓ 采纳 v6] → 切换到预览视图，继续下一轮
  - 不满意 → 点击 [↩ 回滚到 v5] → 回到 v5，调整批注后重新生成
  - 部分满意 → 基于 v6 继续添加新批注 → 生成 v7
```

## 7. 技术实现要点

### 7.1 批注锚定算法

当用户创建批注时，记录：
- 行号 + 列范围
- 被批注文本的**内容哈希**（用于后续重新定位）

当文档被修改（生成新版本）后，用以下算法重新定位批注：

```python
def reanchor_annotations(new_content: str, annotations: list[Annotation]):
    """
    在新版本文档中重新定位旧批注。
    策略：
    1. 优先精确匹配：按行号+列号查找，文本内容一致 → 锚定成功
    2. 模糊匹配：行号偏移±3 行范围内搜索 quote 文本 → 找到则更新锚点
    3. 失败：标记为 outdated
    """
    pass
```

### 7.2 生成 API

```typescript
// POST /api/documents/:id/generate
interface GenerateRequest {
  baseVersion: number;           // 基于哪个版本生成
  chatContext: ChatMessage[];    // chat 上下文
  annotations: Annotation[];     // 待处理的批注
  userPrompt?: string;           // 用户附加指令

interface GenerateResponse {
  newVersion: number;            // 新生成的版本号

  annotationResults: Array<{
    annotationId: string;
    status: 'applied' | 'ignored' | 'partial';

}
```

## 8. 迁移策略

### 8.1 现有批注数据迁移

当前系统已有一批"对话式批注"数据，迁移方案：

1. **对话归档**：将现有批注中的多轮对话压缩为一条"摘要批注"
   - 提取对话中用户的核心意图
   - 用 AI 生成一句话摘要作为批注内容
   - 原对话记录保留在"历史记录"中，但不再作为活跃批注

2. **状态转换**：所有现有批注标记为 `outdated`（因为锚点在新版本系统中需要重新建立）

### 8.2 前端兼容

- 保留现有的 `role=dialog` 气泡 DOM 结构，但简化内部逻辑（移除消息流、打字指示等）
- 批注输入框从 textarea+发送按钮简化为单行输入+Enter 提交
