# Agentic 时代 UI/UX 重设计:三套方案

> 版本:v0.1(方案稿)
> 起因:当前 UI/UX 被指"还是过去时代的设计逻辑"。本文先诊断"过去时代逻辑"
>   具体是什么,再给出三套 agentic 式重设计方案(A 对话中枢 / B 任务中心 /
>   C 活动流工作台),每套含逐部分流程再造,最后给对比与推荐。
> 关系:不动内核与信任模型(升权/数据闸/闸门不动);改的是宿主层的
>   信息架构。既有 agentic 零件(收件箱/升权卡片/助手/Flow C 迭代)见 §6。

---

## 1. 诊断:我们的 UI 哪里"过去时代"

| 维度 | 过去时代逻辑(我们现在的样子) | Agentic 时代逻辑(应该是的样子) |
|---|---|---|
| 人的角色 | **操作员**:填表、点按钮、跑流程 | **指挥者**:说意图、审产物、批决策 |
| 信息架构 | 按**系统数据类型**分页(Runs/Skills/Tools/Lab) | 按**用户意图与任务**组织(我要做什么) |
| 流程发起 | 人找功能(新建→编辑→检查→提交,五步) | 人给目标,agent 给计划,人确认一次 |
| 产出呈现 | 表单与裸数据(JSON、字段、列表) | **产物卡片**(技能卡/检查报告/计划/diff,可读可执行) |
| 系统状态 | 被动等人来查(列表、轮询) | **主动汇报**(agent 推:"x 失败了,原因 y,建议 z") |
| 知识要求 | 用户须懂系统术语(草稿/闸门/闭包) | 用户只须懂自己的意图;术语留给 agent |

一句话:**现在的 UI 假设人是那双手;agentic UI 里人只是那个点头的人。**

### 1.1 我们其实已经有一半零件(别推翻,要组装)

- **收件箱 + 升权卡片**:这就是"系统请求人决策"的标准 agentic 形态,已落地;
- **Lab 助手 + Flow C 迭代**:批注→生成→接受,已是"人审产物"的闭环;
- **plan/promote**:"你审的就是要执行的"已是不变量;
- **信号 WAL + RCA**:agent 可以解释任何一次运行。

问题不是缺零件,是**这些零件散在五个页面里,各自为战,没有一个以意图为中心的主干**。

## 2. 方案 A:对话中枢(Chat-First Shell)

### 2.1 概念

整个应用 = 一场与 Agent OS 助手的对话。**页面不再是目的地,而是对话中生成的产物卡片(artifact card)**;Runs/Skills/Tools/Lab 退化为卡片的"全屏展开视图"。

```
┌────────────────────────────────────────────────────────┐
│ 顶栏:Agent OS · 主题 · 收件箱(n)                        │
├──────────┬─────────────────────────────────────────────┤
│ 任务/产物  │  对话流                                     │
│ 列表      │  你:帮我做个按天气推荐晚餐的技能              │
│ ▸ 晚餐技能 │  agent:计划如下——                            │
│ ▸ 整理下载 │   [计划卡:分解 3 技能,复用 1,新建 2] [批准]  │
│ ▸ 上周失败 │  你:批准                                    │
│           │  agent:首稿完成,首测 62 分                  │
│           │   [技能包卡 v1][测试报告卡:3 过 1 挂]        │
│           │  agent:case2 雨天场景挂了,建议加反例         │
│           │  你:加上,顺便 prompt 精简点                 │
│           │  agent:[diff 卡 v1→v2 62→88 分] [接受][重来] │
│           │  你:接受,发布吧                             │
│           │  agent:[发布计划卡:3 成员 create] [确认]     │
│           │  agent:已发布 v0.1.0 ✅ [去 Skills 看]       │
│           │ ┌─────────────────────────────┐             │
│           │ │ 输入意图…              [发送] │             │
│           │ └─────────────────────────────┘             │
└──────────┴─────────────────────────────────────────────┘
```

### 2.2 逐部分流程再造(方案 A)

| 部分 | 现在 | 方案 A |
|---|---|---|
| 做技能 | Lab 五栏表单 | 一句话 → 计划卡 → 产物卡 → diff 卡 → 发布卡,全部在对话里;表单只作卡片的"展开编辑" |
| 调试 | Debug 页手动断点 | "这个 run 为什么挂?" → agent 出 RCA 卡(假设+证据),你说"重现" → agent 自设断点跑出结果卡 |
| 审查提交 | 点检查→看五关 | agent 主动推送:"你昨天做的技能还没检查,结果是 4 绿 1 黄 [报告卡] [一键修复]" |
| 浏览发现 | 翻 Runs 列表 | "上周哪些 run 失败了?" → agent 出筛选表卡;列表页只是这张卡的全屏态 |
| 新手入门 | 读文档 | 第一句话就有引导:"我可以帮你做技能、调问题、看运行。试试:'帮我做个…'" |

### 2.3 后端需求(A)

1. **Artifact 协议**:卡片类型注册表(plan / skill-pack / gate-report / diff / rca / publish / table),每型一个渲染组件 + 一个结构化 JSON schema(前端组件零分支照主题契约);
2. **对话编排**:assistant 升级为 router——意图识别 → 调用既有能力(scaffold/validate/test-run/plan/debug)并把结果包成 artifact 卡;
3. **卡片即动作**:卡上的按钮映射到既有端点(approve → iterate、确认 → promote),权限语义不变(升权卡也是 artifact 的一型);
4. **对话持久化**:sessions 存 store(刷新不丢;任务/产物列表 = 会话里 artifact 的索引)。

### 2.4 风险

- 对话是唯一入口对**精确操作**反而慢(改一个字段也要说一句)——所以卡片必须可编辑(卡内联编辑,编辑回写结构化 JSON);
- agent 故障时整个外壳瘫痪,需要"降级到经典页面"的硬切换(保留现有页面作 expert mode);
- 工作量大(对话编排 + 卡片协议 + 全部卡型)。

## 3. 方案 B:任务中心(Task as First-Class Object)

### 3.1 概念

顶层概念不是 run/skill,而是**任务**(用户的持续目标:"每周整理下载目录""晚餐推荐")。任务页是活的仪表盘:agent 汇报状态、提出下一步、请求决策。Skills/runs 是任务的下属资源。

```
┌─ 任务:晚餐推荐(每周一 08:00)──────────────┐
│ 状态:运行中 · 上周成功 4/4 · 88 分          │
│ agent 汇报:本周雨多,热汤类推荐占 60%,     │
│   建议加"快手菜"约束 [采纳] [忽略]          │
│ ├─ 技能包 dinner.planner v0.3.1 [卡片]      │
│ ├─ 最近运行(4)[时间线卡]                  │
│ ├─ 待决策(1):新增 net 权限请求 [升权卡]    │
│ └─ 建议(2):case2 反例 / 每周复盘 [建议卡]  │
└─────────────────────────────────────────────┘
```

### 3.2 逐部分流程再造(方案 B)

| 部分 | 现在 | 方案 B |
|---|---|---|
| 做技能 | Lab 里孤立做 | 从任务里长出来:"这个任务还缺什么技能?"agent 提议,做完自动挂回任务 |
| 调试 | 从 Runs 找 | 任务页的"失败"红色区直达,agent 已预读并给假设 |
| 审查提交 | 散落 Lab | 全部汇入任务的"待决策"队列(升权/检查/发布统一一个收件箱语义) |
| 浏览发现 | Runs/Skills 页 | 任务列表即首页(每个任务一张状态卡);Runs/Skills 是任务的二级页 |
| 新手 | — | 创建任务 = 一句话,agent 反问最少必要信息(brief 访谈复用) |

### 3.3 后端需求(B)

1. **Task 实体**(新):{id, goal, brief, skill_refs, schedule?, status};任务与 skill/run 的关联表;
2. **任务状态聚合**:agent 定期(或被问时)汇总任务状态(复用 RCA/usage/信号);
3. **建议引擎**:规则化建议(失败模式/tier 提升/测试缺失)——先是规则,后接 LLM;
4. **待决策统一队列**:supervisor pending + gate warn + publish plan 三类决策统一建模(这是 B 对现有系统最大的结构红利)。

### 3.4 风险

- "任务"是新一等实体,数据模型与迁移成本真实存在;
- 对一次性操作(随便跑个 run)反而绕路——需要"快捷动作"旁路;
- 建议引擎的规则质量决定体验下限。

## 4. 方案 C:活动流工作台(Stream/Canvas)

### 4.1 概念

一条时间流承载一切:run 完成、检查报告、升权请求、助手建议、发布事件——像 git log 遇上 activity feed。每个条目可展开成完整 artifact,动作就地完成(批准/拒绝/重试/回滚)。没有"页面",只有流 + 过滤器。

```
┌─ 流 ▾ 全部|决策|失败|技能|运行 ─────────────┐
│ 10:42 ✅ run dinner.planner 完成 88 分 [展开] │
│ 10:40 ⚠️ 升权请求:ops.cleanup 调 L3 [批/拒] │
│ 10:31 📋 检查报告:dinner v0.2 = 4绿1黄 [修复] │
│ 09:58 🤖 建议:下载目录有 3 个重名包 [看看]   │
│ 09:12 ❌ run ops.janitor failed [RCA] [重跑] │
│ 09:00 🚀 已发布 weather.query v1.2.3        │
└───────────────────────────────────────────────┘
```

### 4.2 逐部分流程再造(方案 C)

| 部分 | 现在 | 方案 C |
|---|---|---|
| 做技能 | Lab 深页 | 流里一张"工作底稿卡"置顶(常驻草稿),其余事件从它下面流过 |
| 调试 | 进 run 详情 | 失败条目展开即调试台(断点/干预内嵌) |
| 审查提交 | 各页分散 | 决策类条目过滤视图 = 统一工作队列 |
| 浏览发现 | 列表页 | 流本身就是;搜索/过滤器替代所有列表页 |
| 新手 | — | 流的第一条是 agent 欢迎卡,教前三句话 |

### 4.3 后端需求(C)

1. **统一事件模型**:把信号 WAL + pending + gate + publish 折叠成一个 host 级事件流(只读视图,不改动内核信号);
2. **流内动作**:条目按钮直达既有端点(升权作答/重跑/跳调试);
3. **常驻卡 pin**(工作底稿)。

### 4.4 风险

- 流对"深度编辑"不友好——编辑器仍需全屏(卡片展开态);
- 信息密度高,新手淹没风险,需要好的默认过滤;
- 是三套里改动最表层的(事件流是只读聚合),但也是最容易做成"又一块仪表板"而忘了意图的。

## 5. 三套方案对比

| | A 对话中枢 | B 任务中心 | C 活动流 |
|---|---|---|---|
| 人的角色 | 对话指挥 | 目标拥有者 | 流式监督 |
| 新骨架成本 | 高(对话编排+卡片协议) | 中高(Task 实体+聚合) | 低(事件流是只读聚合) |
| 精确操作 | 弱(需卡片内联编辑) | 中 | 中 |
| 新手友好 | 最强 | 强 | 中 |
| 故障降级 | 必须有经典模式兜底 | 页面仍在,降级自然 | 自然 |
| 与现有零件复用 | 收件箱/升权卡/Flow C 全是卡型 | 待决策队列=收件箱泛化 | 全是流的条目 |
| 主要风险 | 工作量与故障面 | 新实体迁移 | 变成另一块仪表板 |

## 6. 推荐路线

**A 为方向,B 的概念借用,C 先做。**

1. **第一步(C,2-3 周)**:统一事件流 = 最快的"agentic 感"——把信号 WAL + 升权 pending + 闸门报告 + 发布事件聚合成首页活动流,决策条目就地可办。不动任何内核语义,现有页面全部保留为条目展开态。
2. **第二步(B 的概念,不建实体)**:先不建 Task 表——用**对话里的 brief 卡 + 命名空间包**充当轻量任务(任务 = 一个包 + 它的最近事件过滤视图)。验证"任务中心"是否真好用再决定要不要实体。
3. **第三步(A 的主干)**:对话输入框全局化(每页都有),artifact 协议从 C 的条目类型里长出来(事件条目 = 最早的卡型注册表)。当卡型 ≥6 种时,对话中枢就是把流倒过来(意图在上,产物在下)。

**立即可用的判定**:如果第一步做完,新用户首页从"Runs 列表"变成"活动流 + 顶部意图输入框",agentic 感就成立了——后面两步是加深,不是补课。

### 保留不动的(架构红线)

- 升权/数据闸/五关/plan 原子提交:agentic 改的是体验层,信任模型一个字不动;
- 组件零分支/六主题契约:新组件(卡片/流)全部走 token + copy;
- 专家模式(现有五页)永久保留:agent 故障与用户偏好都需要它。
