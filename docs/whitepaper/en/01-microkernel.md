# Microkernel & Execution Model

> Chapter: 01 · Status: Implemented (true pause semantics landed 2026-09-29; see §6) · Sources: `agent_os/src/agent_os/kernel/runner.py`, `agent_os/src/agent_os/kernel/checkpoint.py`, `docs/DESIGN.md` §1-3

## 1. Overview

The Kernel Runner is the microkernel of Agent OS — the concrete landing point of the mapping-table row "microkernel (scheduling + permissions + IPC) → Kernel Runner" — and it does exactly three things: **flow control**, **permission control**, and **IPC** (docs/DESIGN.md §1, axiom 1; the `Kernel` class at `kernel/runner.py:156-200`). All nine functional subsystems (Providers, Tools, Skills, Context, Logic, Sidecars, Telemetry, Memory, Blackboard) live outside the kernel; the kernel holds only their contract handles, wired together by `KernelBuilder` (`runtime/builder.py:149-247`). In the execution model, a Run is a process, a SkillFrame is a stack frame, and the agent loop is the per-frame executor; checkpointing and power-cut recovery (`kernel/checkpoint.py`) belong to the kernel's reliability mandate. This chapter deepens §3.1-3.2 of the executive summary: rather than restating the layering, it pins down the loop's exact decision order, where each arbitration point sits, and how the recovery algorithm works.

## 2. Motivation & Background (Why)

Agent loops have a structural gravity: every new capability — compression, supervision, retries, persistence, human-in-the-loop — is cheapest to add by dropping it into the loop body. A few iterations later the loop is an indivisible lump: mechanisms entangle, swapping a compressor means touching dispatch code, and there is nothing left to remove when you want a bare-model ablation baseline. Agent OS counters this by making "what may stay in the kernel" an executable criterion (docs/DESIGN.md §1, axiom 1):

- **F**: without it the loop cannot advance (frame stack, dispatch, cancellation);
- **P**: it is a permission/veto arbitration point (whitelist checks, verdict arbitration);
- **I**: it is the only common channel between subsystems (signal bus, RunControl).

Only what satisfies at least one criterion stays; everything else is pushed into a subsystem. The other half of the corollary matters just as much: the kernel does **not** execute logic code (Logic Kernel — a single execution point is what makes execution arbitrable), does **not** assemble prompts (Context — a single token-accounting dialect), and does **not** persist (Telemetry — WAL durability semantics are incompatible with the sidecar fire-and-forget model, §10). This is not aesthetics: a scattered arbitration point is no arbitration point, and the audit surface grows linearly with kernel size.

The second key decision is to **implement the call stack directly as Python await chains** instead of building an explicit scheduler (docs/DESIGN.md §3.1): a suspended parent frame is an `await` point, a completed child frame is a coroutine return, and asyncio cancellation propagates down the stack for free. The cost is that coroutine stacks are opaque — sidecars cannot inspect them and RunControl cannot address into them. Frames are therefore still registered explicitly in a `FrameStack` (`kernel/stack.py:15-27`): three views (active frames, by-id index, parent-child adjacency) serving `pre:frame.pop` vetoes, frame-tree inspection, and checkpoint serialization. The implicit stack owns control flow; the explicit stack owns arbitration and persistence — the execution model's central "best of both" trade.

## 3. Problem Statement (What It Solves)

1. **Privileged operations scatter, leaving nothing to arbitrate.** A model that can call tools, invoke sub-skills, and generate code gives supervision nowhere to attach if each path reaches the outside world on its own. All privileged operations must converge on a single dispatch gate.
2. **Sub-task internals pollute the parent frame.** A sub-skill that runs 20 steps and ingests thousands of lines of tool output makes the parent both expensive and diluted if everything flows back. A child's whole transcript must collapse into one return value on pop ("isolation over compression", docs/DESIGN.md §2.3).
3. **Interruption creates orphan tool_calls.** If cancellation lands between "assistant emitted tool_calls" and "tool_result written", the next request carries an unpaired call and most provider APIs reject it outright. Pairing atomicity (§7.4 invariant 2) must hold on the interrupt path too.
4. **Recovery after a power cut equals re-running from scratch.** If a long run dies at step N, and recovery means repaying N-1 LLM calls and replaying tool side effects, the reliability mechanism has no economic point.
5. **A runaway run cannot stop at a clean boundary.** When budget runs out or a loop spins, cutting at an arbitrary instruction boundary leaves the frame tree half-mutated. Stops must happen only at dispatch boundaries (safe points).
6. **Failure propagation needs lethality tiers.** An ordinary child failure (say, a tool timeout) must not bring down the whole tree; conversely, a run-level verdict like budget exhaustion must never be swallowed by some frame's `try/except`.

### 4.2 The Single-Frame Agent Loop: Decision Order Is Security Semantics

The step order in `_frame_loop` (`runner.py:433-542`) is deliberate — arbitrate first, act second:

```
run_frame(frame)                       # runner.py:389
  ├─ pre/post:frame.push; depth backstop checked on push (stack.py:29-39)
  └─ loop (each step):
     1. safe point: check _stop_flags[run_id] → RunAborted; check  (runner.py:437-445)
        per-frame stop flag (set by cancel_subtree) → SubtreeCancelled
        (subtree terminates, the run survives)
     2. emit pre:step, arbitrate verdicts: Stop/Veto/Pause → abort;  (runner.py:446-449)
        InjectMessage/ForceCompress land via RunControl, continue    (runner.py:361-375)
     3. consume per-frame force-compress flag → context.maintain/build (runner.py:450-453)
     4. pre:llm.request → _llm_call → post:llm.response              (runner.py:454-474)
        (RunConfig.stream is on by default: when caps support
        streaming, _stream_call runs the chunk loop emitting
        post:llm.chunk per chunk, otherwise falls back to chat;
        dict-shaped tool_calls normalized to ToolCall on entry, runner.py:456-467)
     5. response appended + accounting (await account: run-level
        breach → hard failure; then manifest limits frame/subtree
        budgets — root breach kills the run, other breaches abort
        the subtree; see this section's closing paragraph)           (runner.py:475-476)
     6. no tool_calls → outputs validation: failure writes an error
        observation and retries; 2 consecutive failures
        (_OUTPUT_VALIDATION_MAX_FAILURES) → frame failure            (runner.py:477-496)
     7. dispatch each call; on CancelledError write an interrupted
        placeholder tool_result first, then re-raise — pairing
        atomicity holds on the interrupt path                        (runner.py:497-508)
     8. post:step (call-signature list, LoopDetector's observation
        surface) + StatusBoard                                       (runner.py:524-542)
  ├─ pre:frame.pop is vetoable: Veto → correction observation into
  │  frame context, back to loop; Stop → RunAborted; pop_ok only
  │  with no veto                                                    (runner.py:406-424)
  └─ post:frame.pop; the frame's transcript collapses into one tool
     result in the parent as the coroutine returns
```

Two trade-offs are worth stating explicitly. First, **the output-repair breaker is set to 2** (`runner.py:124`): when the final answer fails `outputs` schema validation the model gets one chance to self-correct (error observation written back, §3.2), and consecutive failure fails the frame — fewer gives the model no room to repair, more is gambling tokens on probability and violates the "every recovery path has its own circuit breaker" rule. Second, **accounting and budget verdicts live in the kernel, not in a sidecar** (`runner.py:2156-2201`): `max_steps`/`max_cost` are hard RunConfig boundaries and must propagate as `RunAborted`/`BudgetExceeded` (`kernel/errors.py:26-34`) that no frame can swallow; the BudgetGuard sidecar covers the host-configurable soft-degradation case (stop→pause) instead (§2.4's failure-lethality layering).

**Frame/subtree-level budgets entered kernel enforcement on 2026-09-28** (`_check_subtree_budgets`, `runner.py:2203-2282`). The mount point is the manifest `limits` block: `max_cost` is a new additive field (default `None`; a non-numeric or boolean value raises `SkillLoadError` at load time, `skills/manifest.py:26-37`), while `max_steps` is a pre-existing declaration that now has an enforcement point. The two fields deliberately use different scopes: `max_steps` caps the frame's **own** agent-loop steps (every existing manifest in the repo declares it in this frame-local sense, mirroring RunConfig.max_steps' "whole-run total steps"), while `max_cost` caps the **summed cost of the frame and all its descendants** — cost accumulates along a subtree, so the budget reads "how much this subtree may spend in total". The check runs at the end of `account()`: the run-level checks are unchanged, then budget frames are collected by walking the `parent_id` chain (a chain with no budget declarations takes a zero-cost fast path; the subtree sum reuses `_collect_subtree`; `account` became async for this — the ancestor branch must await `cancel_subtree`; the compression drain `_drain_compress_usage` and the `ctx.chat` accounting point run the same check). The write path is untouched: a parent frame's usage still excludes its children, and aggregation stays on the read side (§4.6 `subtree_usage`). Breaches are tiered by where the budget frame sits: the root frame → `BudgetExceeded` kills the run; the current frame → `SubtreeCancelled("budget: ...")`; an ancestor → `cancel_subtree`, terminating the subtree while the invoke boundary folds the outcome into an interrupted error observation and the run continues. Before triggering, a `budget.exceeded` signal is emitted (the first emitter of this frozen-catalog entry, `api/v1/signals.py:101`; payload carries depth/frame_id/skill plus max_cost/max_steps/subtree_cost/subtree_steps), exactly once per budget frame (`_budget_tripped` dedup, process-local and not checkpointed, idempotent across resume). The layering with BudgetGuard is unchanged: kernel enforcement is the hard boundary, BudgetGuard remains the host-configurable soft-degradation policy layer; `budget.warning` (80%) still has no emitter.

### 4.3 Dispatch & Frame Push: One Gate for Every Privileged Operation

`_dispatch_call` (`runner.py:694-763`) is the single entry point for all calls, routed by name:

- `skill.<name>` / `skill__<name>` pseudo-tools → `_invoke_skill` pushes a frame (both prefixes are accepted — docs/DESIGN.md §3.3 writes `skill__<name>`, while the repo's example skills and tests actually use `skill.<name>`; the code wins, see `runner.py:697` and `runner.py:1012-1015`);
- `python_orchestrate` → sandbox orchestration (`runner.py:878-1008`; syscall callbacks re-enter `_dispatch_call`, no privilege gain);
- `ask_supervisor` → suspend in place awaiting adjudication (`runner.py:764-807`);
- everything else → manifest whitelist check (not listed → structured error observation, never executed) → `pre:tool.call` arbitration (Veto skips dispatch and writes the reason back, Modify patches args, Stop/Pause aborts) → Tool Registry pipeline → `post:tool.call`.

`_invoke_skill` (`runner.py:1009-1103`) is where the frame tree grows: whitelist check → `pre:skill.invoke` → depth backstop (beyond `max_depth` raises `MaxDepthExceeded`) → **escalation gate** (when the callee's derived tier exceeds the caller's, args are schema-validated first, then adjudicated through the supervisor channel, `runner.py:1036-1057`; the mechanism itself belongs to the escalation chapter) → `make_frame` builds the child and registers the parent's `call_id` (for checkpoint pairing) → the child inherits the callee's derived tier → `await run_frame(child)` pushes, parent suspends. Failure propagation is tiered here: `MaxDepthExceeded`/`RunAborted` re-raise untouched, while every other child exception collapses into an error observation for the parent (`runner.py:1084-1100`, `hint` carried across) — ordinary failures are left for the parent LLM to repair; run-level verdicts travel the stack straight to the Run boundary.

### 4.4 Verdict Arbitration & RunControl: Policy Outside, Adjudication Inside

When several SYNC sidecars return verdicts on the same `pre:*` signal, the kernel's `_arbitrate_pre` (`runner.py:354-358`) takes the **first non-Allow** (the emit side already ordered by priority; `None` counts as Allow) — a deterministic verdict independent of sidecar count. Sidecars never interrupt the loop directly: everything they do to a run goes through RunControl (`kernel/control.py:30-107`) into kernel state — `stop`/`pause` set the `_stop_flags`/`_pause_flags` tables and the runner itself checks them at the next safe point (**stop wins** when both are set), raising `RunAborted`/`RunPaused` (the latter lands PAUSED at the run boundary, emits run.paused, persists the checkpoint as usual, and can be resumed, 2026-09-29); `inject_message` appends a USER/INJECTED message; `force_compress` sets a flag in the frame's working memory, consumed before `maintain`. This is axiom 3 in engineering form: **policy (what to review) lives in sidecars; adjudication (fail-closed, priority, timeouts) lives in the kernel**. Cancellation happens only at dispatch boundaries — there is no "deleted half of it, then got cut" frame.

**The external event entry has landed at the host layer, with event batching for the running channel completed on 2026-09-29**: `POST /api/events` (`host/web/app.py:819`) routes by run state through three channels — a running run is split by `[events].batch`: with batching on (the default), the event entry `{type, text, at}` is appended over the cross-thread bridge into the root frame's working-memory queue `working["_event_queue"]` (action="queued"), and the runner drains it before the next build into a single batch-header message (`[event 批处理 N 条]` plus a numbered list, USER/INJECTED, meta `{"kind":"event-batch","count":N}`; beyond `batch_max` the oldest entries are dropped and counted in `dropped`); with batching off, the original behavior stands — immediate injection into the root frame via `ctl.inject_message` (action="injected"). A paused run has the event appended to its checkpoint root frame's context.messages and then goes through the existing resume (action="resumed"); with no target, a new run is started with the given skill (action="started", input defaulting to `{"event": {...}}`). The drain point (`Kernel._drain_event_queue`, `runner.py:470-506`, call site :584) sits after the pre:step safe point and before build, in the same region where FORCE_COMPRESS is consumed, and is the **only merge point** for batch headers: the book's in-step multi-point draining ("inject whenever any tool.result returns") is deliberately rejected — an in-step merge would land between the assistant tool_calls and their TOOL results, breaking §7.4 pairing invariant 2; the price is that an event is seen at most one step late, in exchange for pairing atomicity and "resume is draining" (the queue persists with the checkpoint's working serialization, so the first build after resume drains it naturally, zero hooks). The batch header's count also carries the attention-marking function of a status-bar event marker (evaluation conclusion: the status bar is always 0 right after a drain, so no separate events row is listed). Events land at the root frame only; subframe context purity is untouched. Configuration is the `[events]` section's three keys (strict, all defaults when the section is absent): `batch = true` / `batch_max = 50` / `event_text_max = 2000` (event text truncation). This cashes out "the kernel stays turn-based and wake sources belong to the host": zero contract changes, and the kernel only gains a single drain point before build; the host signal `event.received` is delivered over the per-run hub (visible in SSE live and replay) and deliberately stays out of api/v1 and trace.jsonl. A persistent/cross-run event queue, per-frame addressed injection, event filtering/rate-limiting, and `monitor_shell`/`connect_channel` remain open.

### 4.5 Checkpoint & Recovery: The Trajectory Is the Whole State

Checkpoints follow the WAL principle (docs/DESIGN.md §10.2): a fully persisted frame transcript *is* the checkpoint. `dump_checkpoint` (`kernel/checkpoint.py:126-174`) serializes run state (usage, run-level tool state, the escalation grant ledger) and every frame (context, working, pinned, usage, tier, principal, call_id) into version-headed `{"v": 1}` JSON (`checkpoint.py:73`). Recovery is not re-running: `resume_from_checkpoint` (`checkpoint.py:321-394`) rebuilds the Run and frame tree, skips frames that already carry a `result`, settles survivors **deepest-first** (children resume to DONE before parents settle, so parents read real results), and re-enters the loop at the deepest unfinished frame with its full context — the number of remaining LLM calls is exactly countable; its `finally` mirrors `run()` by calling `_release_run` (`checkpoint.py:387-394`), so registered background frames, telemetry handles, and tool temp dirs do not linger.

A power cut leaves three kinds of pairing damage in a frame's context, settled one by one by `_settle_unpaired_calls` (`checkpoint.py:281-320`): (1) a successful result already exists → untouched; (2) only the error observation from the crash exists, but the child frame created by that call (matched by `call_id`) is DONE → **rewritten in place** to the child's real result; (3) no result at all and no child frame → an `interrupted` placeholder is appended (same shape as §3.1's interrupt pairing). Two kinds of suspended calls are *not* crash damage and never get placeholders: a frame suspended in `ask_supervisor` re-asks and settles via `working["_pending_ask"]` (`runner.py:808-834`), and one suspended at the escalation gate re-walks the gate via `working["_pending_escalation"]` (`runner.py:1279-1313`) — approval rebuilds and runs the child on the spot, denial writes `PERMISSION_DENIED`, and pairing atomicity closes naturally. `PeriodicCheckpointer` (`checkpoint.py:175-224`), a bus subscriber, overwrites a "latest scene" file every N `post:step` signals, moving the crash-recovery point from end-of-run to the last N steps; persistence failures are logged, never fatal to the run.

### 4.6 Concurrency Primitives: All Three in Place

Serial `await` is the default. `spawn_frame`/`wait_frame` (`runner.py:1530-1563`) implement §3.4's background frames: whitelist/depth/escalation checks identical to invoke (the spawn pipeline is split into `_spawn_whitelist_check`/`_spawn_gate`/`_spawn_register`, `runner.py:1464-1845`); the child runs as an `asyncio.create_task`; join degrades to reading the terminal state (exceptions re-raise as-is; a subtree killed by cascade cancel raises `SubtreeCancelled` instead, and the code skill decides whether to catch it); parent and child exchange rolling state over the StatusBoard. The fork/join fan-out `parallel_invoke` has landed (`runner.py:1795-1859`, helpers `_parallel_branch`/`_parallel_unsafe_tool`/`_parallel_cancelled`/`_parallel_cancel_all` at :1860-1931; code skills reach it via `LogicContext.parallel()`, `kernel/logic_context.py:149-156`, contract `api/v1/logic.py:222`): a serial pre-flight pass reuses the spawn front-end per branch; `all_settled` is a structured gather that never re-raises, and a failed `depends_on` prerequisite marks the dependent branch cancelled without starting it; `first_success` wins exactly once via a done-flag, cascade-cancels the losers with `cancel_subtree`, waits for acks up to `settle_timeout`, and settles idempotently at the single parent-side join point; hard failures (RunAborted/BudgetExceeded/MaxDepthExceeded) are not folded and kill the run; `max_concurrency` is enforced with a Semaphore. The `concurrency_safe` contract field reserved at `api/v1/tools.py:105` gets its first enforcement consumer here: a code branch whose whitelist contains an undeclared tool degrades to serial execution at full concurrency allotment (fail-safe, not rejection; logged), while prompt branches are exempt. Two companions landed alongside: §5.2's subtree cascade cancel (`Kernel.cancel_subtree`, `runner.py:1954-1993`; `RunControl.cancel_frame`, `kernel/control.py:63-71`) and the subtree accounting read view (`Kernel.subtree_usage`, `runner.py:2062-2104`; `RunControl.get_subtree_usage`, `kernel/control.py:97-103`) — the former is the engine foundation for first_success loser teardown and `subagent_cancel`-style combinators, the latter sums all nine Usage fields over a subtree, mirrored per frame row as a `subtree` column in the RCA usage panel (`host/web/rca.py:122-167`).

## 5. Effects & Verification (Results)

Test evidence (this chapter's direct surface): 137 tests across 16 files in `tests/kernel/` plus 3 in `tests/telemetry/test_trace_checkpoint.py` — 140 tests, all passing in a measured run; the full repo collects 1863 tests via `pytest --collect-only` (1813 passed / 10 skipped / 40 xfailed at the time of writing). Key anchors:

- **Execution-model vertical slice** (`tests/kernel/test_fib_slice.py`, 5 tests): the recursive skill `demo.fib` (`agent_os/skills/skills.yaml`; fib(n) first invokes itself for fib(n-1), then calls the sandbox tool to sum the last two) returns the correct sequence end to end; frame-tree shape assertions — fib(5) pushes exactly 4 frames at depths 1-4, exactly 10 LLM calls, exactly 3 sandbox executions; **frame-isolation assertions** — the parent's second request is `[SYSTEM, USER, ASSISTANT, TOOL]`, the child's whole trajectory collapsed into one `{"ok": true, "value": {"seq": [0,1,1,2]}}` tool result, and the SYSTEM prefix is byte-identical across adjacent requests of the same frame; with `max_depth=2`, fib(4) raises `MaxDepthExceeded`; `bad_brain` triggers `OutputValidationError` after consecutive failures.
- **Power-cut recovery** (`tests/telemetry/test_trace_checkpoint.py`, 3 tests): a power-cut exception is injected at the 6th LLM call of fib(5); a fresh kernel resumes from the checkpoint and needs **exactly 5 more calls** (`len(mock2.recorded) == 5`) to return the full sequence — "recovery is not re-running" pinned to a call count; the checkpoint JSON contains the version header, run usage, mixed running/done frame states, and complete frame contexts.
- **RunControl** (`tests/kernel/test_run_control.py`, 9 tests): pause lands a resumable suspension at the next safe point (RunPaused → PAUSED + run.paused, resumable via resume), stop semantics unchanged; injected messages are wrapped as USER/INJECTED and appear in subsequent LLM requests; injection/force-compress on a missing frame is dropped without crashing the run; `get_frame_tree` returns the nested tree; `get_usage` returns the accounting snapshot; `cancel_frame` sets per-frame stop flags and DFS-collects the subtree, which reaches a terminal state (SubtreeCancelled) while the run survives.
- **parallel_invoke** (`tests/kernel/test_parallel_invoke.py`, 12 tests): results returned in branch order; per-branch fault isolation and the depends_on cascade; per-branch whitelist/depth pre-flight; malformed batches raise SkillLoadError; first_success locks the winner and cascade-cancels the losers, all-fail returns the error entries; max_concurrency caps parallelism; the concurrency_safe gate degrades to serial; a run stop aborts an in-flight batch; BudgetExceeded is not folded; checkpoint resume refires the whole batch.
- **Subtree accounting** (`tests/kernel/test_subtree_usage.py`, 4 tests): `subtree_usage` sums over descendants; the root frame's subtree equals run-level accounting; an unknown frame returns a zero Usage; `RunControl.get_subtree_usage` delegates to the kernel.
- **Periodic checkpoint** (`tests/kernel/test_periodic_checkpoint.py`, 3 tests): overwrite-writes on `post:step` counts; counting stops when the run ends.

Ripple effects: the signal catalog plus the explicit frame tree are the shared foundation for later systems — Telemetry subscribes to the same stream as a privileged subscriber and lands it as JSONL WAL (`builder.py:216-218`); the debugger (`kernel/debug.py`) and replay build directly on the bus and frame contexts; the escalation gate and the clean-context invariant both hang off this chapter's dispatch point and frame-isolation semantics — were `_invoke_skill` not the single push site, the escalation model would have nowhere to stand. For ablation, `KernelBuilder` can run a bare loop with only a MockProvider and an empty tool table (the microkernel-purity acceptance of docs/DESIGN.md §14.2; `runtime/builder.py:17-18`), and much of the test suite runs on exactly such minimal assemblies (e.g. `tests/helpers/kernels.py:38-73`).

## 6. Limitations & Boundaries (Limits)

1. **In-flight batches do not survive checkpoints, and branch usage is not rolled back.** `parallel_invoke` behaves like spawn: batches carry no checkpoint pairing, so a power cut loses an in-flight batch; the code parent frame re-runs wholesale on resume and refires the whole batch, and callers must make that idempotent (`runner.py:1616-1617`). Branch usage is booked into the run in real time, and a first_success loser's consumption is not refunded after cascade cancel — consistent with the established "in-flight side effects are fait accompli" semantics. Subtree cascade cancel is likewise point-in-time: frames spawned after the cancel starts are outside the cancel set, and per-frame stop flags are not persisted.
2. **pause is a checkpoint-resumable suspension, not in-place continuation (the boundary after true semantics landed on 2026-09-29).** `RunControlImpl.pause` sets an independent `_pause_flags` entry (`kernel/control.py:43-50`); the safe point (stop wins) raises `RunPaused`, and the run boundary lands PAUSED, emits `run.paused` (never run.aborted), and persists the checkpoint as usual. Continuing means checkpoint serialization + resume on a rebuilt kernel (whose config may change — §2.4's "top up the budget, then continue"), i.e. re-entering the loop from the latest checkpoint rather than the exact paused instruction. The supervisor-await and debug-session in-process suspensions are two separate channels (the run stays RUNNING); the CLI has no pause subcommand.
3. **The kernel does not enforce `max_wall_time`.** `Kernel.account`'s run-level checks cover only RunConfig `max_steps`/`max_cost` (`runner.py:2193-2200`; the manifest `limits` frame/subtree budgets are checked separately — see the closing paragraph of §4.2); the wall-clock cap lives in the BudgetGuard sidecar (`sidecars/builtins.py:72-73`), configured from host TOML rather than the `RunConfig.max_wall_time` field — with no sidecar assembled, a run has no wall-clock breaker.
4. **Spawned background frames do not survive checkpoints.** The `_spawned` task table (bucketed per run as `dict[run_id, dict[frame_id, (parent_id, task)]]`) and `_stop_flags`/`_frame_stop_flags` are in-process state (`runner.py:226-238`); after a power cut the spawned subtree is gone, and the recovery semantics are "the code parent frame re-runs wholesale and re-reaches the spawn gate" (comment at `runner.py:1501`) — side effects already produced by background frames are neither replayed nor settled, so callers must make them idempotent.
5. **Single event loop, coroutine-level parallelism.** Parallel branches share one asyncio loop; a CPU-bound code skill blocks its siblings (noted in docs/DESIGN.md §3.4). Multi-machine distributed execution is an explicit non-goal in §17.
6. **Checkpoint schema v1 has no migration path.** A version mismatch raises `ValueError` outright (`checkpoint.py:329-330`); format evolution survives on additive fields with defaults (e.g. tier/principal default recovery, `checkpoint.py:234-246`), and there is currently no answer for breaking changes.
7. **Safe points cannot govern in-flight side effects.** Stops take effect only at step and dispatch boundaries; when a force-stop hits an orchestration script already inside the sandbox, "the syscalls already executed have already happened" — the kernel can only report the executed list back to the model for compensation decisions (`runner.py:986-995`). No transactional rollback; built-in transactions/compensation are explicitly out of scope in §3.2.
8. **Cost breaking depends on a price table.** Without one, `usage.cost` stays 0 and neither `max_cost` nor BudgetGuard ever fires (fail-open on money); assembly can only warn (`runtime/config.py:583-588`).
9. **Boundaries of streaming consumption.** The runner streams by default (`RunConfig.stream=True`, falling back to chat when caps do not support streaming or the Mock has no `stream_scripts`); no retries mid-stream — the Manager's commit-point semantics: stalls/errors before the first chunk retry with backoff, errors after the first chunk raise directly (`providers/manager.py:195-258`); a resumed run re-executes the whole step (streaming does not change checkpoint granularity); `post:llm.chunk` is ASYNC-observation only, sidecars do not adjudicate per chunk; token-level UI is not done (the Web hub's 2000-entry ring-buffer crowding problem is deferred), and the web_platform direct-to-chat path is not streaming.
10. **Event batching drains only at the root frame and only before build (the boundary after landing on 2026-09-29).** Events for a running run enter the root-frame queue `working["_event_queue"]` via `POST /api/events` and merge into a single batch-header message only before the next request assembly — an event is seen at most one step late. In-step multi-point draining ("inject whenever any tool.result returns") is rejected by decision, because it would insert messages between the assistant tool_calls and their TOOL results, breaking §7.4 pairing invariant 2 (§4.4). Per-frame addressed injection (delivering an event straight to a given subframe), event filtering/rate-limiting, and cross-run queues remain open.
